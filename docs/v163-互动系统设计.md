## A.2 统一 env 契约（核心设计）

**问题**：主线 12 章是**单串**的（挂在 `rec` 上），夜话 24 条是**会话**的（挂在 thread 上）。两套数据，但**应该共用一套 `when` 语法和一个求值器**。

**方案**：不做两套求值器。定义**一个 env 契约** + **两个 env 生产者**，`whenOK()` 只认契约。

```
soloEnv(item, rec, ctx)   → 单串 env（主线 12 章 / 单串事件）
thEnv(thread, ctx, now)   → 会话 env（夜话 24 条）  ← 现有，做加法扩展
whenOK(when, env)         → 唯一求值器（两个 env 都能喂）
whenNeed(when, env)       → 唯一提示器
```

契约规则：**env 里不存在的键，`whenOK` 一律判为「不满足」并给出保守提示**（不能判 `true`，否则老存档会误解锁全部章节）。

## A.4 复合条件：最小语法

**需求**：修订后的门槛大量需要「A 或 B」（见 B.1）。

**设计：只加两个键，不动顶层结构。**

```js
// 现状（全键 AND）—— 13 条现有事件全都是这个形态，行为不变
when: { days: 7, members: 2 }

// 新增：OR
when: { stage: 4, bond: 150, anyOf: [ { plays: 120 }, { days: 45 } ] }

// 新增：NOT
when: { not: { gifted: 1 } }

// 可以嵌套（anyOf 的子项本身是完整的 when 对象）
when: { stage: 2, anyOf: [ { idle: 7 }, { days: 40 }, { bond: 90, room: 2 } ] }
```

**求值规范（架构师照此实现，约 15 行）：**

```
ok(when, env):
  when == null        → true
  when.always         → true                      // 保留现有短路
  when.not            → !ok(when.not, env)         // 新增
  逐键判定（跳过 always / not / anyOf）→ 任一不满足 → false
  when.anyOf          → anyOf.some(w => ok(w, env))// 新增；anyOf 缺失视为 true
  全部通过            → true
```

**为什么不用顶层数组表示 OR**：现有 `whenOK(when, e)` 的入参是对象，13 条事件的 `when` 全是对象；若顶层允许数组，`duoPick(ev, ranked)`（:3126）里 `w.occasion` / `w.pers` 的取值会炸。**用 `anyOf` 键 = 零向后兼容风险。**

**为什么不加 `allOf`**：顶层对象本身就是 AND，`allOf` 是冗余糖。**不加。**

### B.1.3 🚨 结论：三处设计事故

> **事故一（最严重）：第 12 章终章要玩家等 365 天。**
> `days≥365` 是纯日历量，**玩家无法用任何行为加速**。365 天里前 80 天 bond 就到 240 了、前 45 天 stage 就到 4 了——剩下 **285 天是纯空转**。
> 更致命的是节奏**倒挂**：A 型玩家 **23 天看完前 9 章**，然后**从第 23 天等到第 365 天**才看得到第 10/11/12 章。全书的高潮（卷四）与结局（卷五）全部堆在最后一年，前面 9 章挤在 3 周内放完。这不是小说，这是**前面一口气念完、后面断更一年**。
> **这是会毁掉整个叙事节奏的设计事故，必须改。**

> **事故二：第 10 章要等 180 天（半年）。**
> `days≥180` 在 A 型下是第 180 天，而 stage≥4 只要 45 天、bond≥120 只要 40 天。**第 9 章与第 10 章之间有 135 天死寂**——玩家刚看完"它第一次以人形站在客厅里"（全书情感最强的反转之一），然后半年没有任何新章节。

> **事故三：第 11 章的 `plays≥120` 对轻玩家是 120 天、对佛系玩家是 360 天。**
> 主题上没问题（石心 = 你盘得太多），但**数值量级错了**：1 天盘 1 次是"正常玩"，不是"盘太多"。要 120 天才触发，等于说"玩到第 4 个月你才有罪"。石心应该在玩家**还觉得自己没盘够**的时候就出现，才有反转力。

### B.1.6 ⚠️ 一个必须注意的实现前提：`stage` 靠玩家手动突破

`stage` 只在玩家**主动点「突破」**时才 +1（`canBreak` = growth 够 + 玩家点）。若玩家从不点突破，`stage` 永远停在 1 → **第 3 章之后全线锁死**。

**对策（两条，都写进规范）：**

1. **门槛提示必须带动作按钮**：`whenNeed` 对 `stage` 键的提示不是"要到「蜕形」"，而是"**攒够了，点这里让它蜕形 →**"（现有 `stageInfo().canBreak` 已能判，`app.js:3877` 已有类似提示 UI，复用即可）。
2. **加一条"自破"兜底事件 `d_selfbreak`** —— ⚠️ 规格已按文案策划的两条硬约束改写，见下。

#### `d_selfbreak` 正式规格（列入事件清单）

**动机（文案策划定，已采纳）**：它不是"等不及"，是**它怕你停下来**。它隐约知道你一旦停手它就会淡——所以它自己撑破了，好让你觉得"还值得继续盘"。
这条直接成了**第 11 章石心的引信**：推动它走向石心的不是贪心，是**害怕被丢下**。且与题材池 **T11「它不肯化形」正好互为反面**——一个不肯长，一个不等你点头就长了，**同一份恐惧的两面**。

| 项 | 规格 |
|---|---|
| **判定作用域** | **`soloEnv`（单串），不走 `thEnv`**。原因见下方说明——`stage`/`growth`/`canBreak` 都是**单串量**，放进会话 env 会被聚合成 `stageMax`，"有一只没突破"这件事就判不出来了 |
| **触发条件** | `{canBreak: true, not:{stage:4}}`，且 `growth ≥ 下阶 need × 1.5` |
| **三档具体值** | **45 / 135 / 270**（对应 1→2 / 2→3 / 3→4 三次突破；下阶 need = 30/90/180） |
| **适用对象** | **主串集内逐只判**（集合制改版）；**集外的串只做静默 `stage+1`**（不让 100 只都弹事件）。每个命中的主串**各自**得到一条待读事件（数量由玩家勾了几只决定，默认 1 只） |
| ⚠️ **必须覆盖全部三次** | 只做 1→2 的话，不点突破的玩家照样在第 10 章前死锁（第 10/11/12 章都要求 `stage≥4`）——**D4 只解决了三分之一** |
| **剧本** | 三条 `d_selfbreak`（一条一档），或一条事件内部按 `stage` 分支 |
| **呈现** | 主串详情页 / 沁灵纪页的**一条待读事件**（不是群聊对话）。理由：它必须是"**这一只**"的事 |
| **成本** | 约定 350 字（约 12 行 + 1 结局） |

**为什么判定放在 `soloEnv` 而不是 `thEnv`（这条很重要）：**
`stage` / `growth` / `canBreak` 都是**单串量**。若塞进会话 env，`thEnv` 只会聚合出 `stageMax` / `growthMax`——那 `not:{stage:4}` 就变成"**群里最强的那只没到化形**"，而我们要判的是"**有一只够格了却还停在原地**"。**语义完全错位。**
→ 正确做法：**逐串判**（`soloEnv`），**主串集内命中才弹事件**，集外静默 `stage+1`。这样 100 只串不会同时炸出 100 个事件（O(n) 一次扫描即可，符合硬约束）。
> 附注：如果以后确实需要"会话里任意一只满足某条件"的语义，那要新增一个 `anyMember:{...}` 键，**本次不做**（不过度设计）。

🔴 **硬约束：自破绝不能走突破的付费路径。**

**核实结论（我读了代码，文案策划说的成立）**：`app.js:3486-3510` 的 `spiritBreak()` 里，第 **3500** 行跑 `Spirits.generateImage(item, ..., nextStage, ...)`，第 **3507** 行才 `r1.stage = nextStage`。
→ **`突破 = 一次付费出图`**。自破若走同一条路，等于**在玩家没点任何按钮的情况下替他花钱**——直接踩「0 成本」铁律，而且属于**付费类事故**。

**规定**：
- **自破只做 `stage + 1`，沿用旧立绘**（不调 `generateImage`，不写 `imgHistory`）。
- UI 给一句：**「它自己撑破了，样子还没跟上。」**
- 旁边配一个**可选**的「**✨ 重画**」按钮，**玩家点了才花钱**。
- 这样既守住铁律，还白捡一个自然的付费点——而且"样子还没跟上"这句话本身就是剧情。

#### D5 详规：多主串下的 CG 遍历顺序与跳过语义（v163 改版）

**为什么必须写清**：主串从 1 只变 N 只后，出图逻辑从"单只流程"变成"**批量流程**"。批量流程里一个 `return` 写错，就会**一只没定设定 → 整批都不出图**。

**遍历顺序**：按 **`threadRank`（:3077）升序**遍历有效主串集（`bornAt || createdAt` 升序、`id` 兜底）。
- 选它是因为 `threadRank` 是**稳定排序**：串的先后不会因为 `star` 变动或勾选顺序而抖动，**出图顺序可复现**。

**跳过语义（逐条）：**

| 情况 | 动作 | 是 `continue` 还是绝不能 `return` |
|---|---|---|
| 该只**未定设定**（`spiritNeedsSetup(rec)`） | **跳过它**，并在它的章末给一句："**先给它定个设定，画出来才准**"（点击跳设定向导） | ✅ **`continue`** —— 继续判下一只 |
| 该只**不在 `stage` 出图范围**（`!needCg(stage)`） | 跳过（沿用现有规则） | ✅ `continue` |
| 该只 **`rec.cgs[key]` 命中缓存** | 跳过，**不重复出图** | ✅ `continue` |
| 该只**刚失败过**（`_cgErr` 在 10 分钟内） | 跳过，防烧额度 | ✅ `continue` |
| 该只**批量出图进行中** | 现有 `_cgBusy` 是**全局互斥**（app.js:3333） | ⚠️ **保留全局锁**，但锁的作用域是"**同一时刻只有一个出图请求**"，**不是"一只失败就中止整批"** |

> 🔴 **一句话纪律**：**`continue`（跳过这一只）可以，`return` / `break` / `throw`（中止整批）绝对不可以。**
> 批量循环里任何一处提前返回，都会让"**因为第 3 只没定设定，第 4/5 只的主串也不出图了**"——这是改集合制后最容易埋进去的一个 bug。

**"已定设定"不过滤主串集**：玩家勾了就该在主串列表里看到它（`mainSetOf` 不过滤，见 C.2.2）。只在 **CG 环节**过滤 —— 前者是"能不能选"，后者是"能不能画"，两件事。

**结局可达性自查：**

结局内的时间跳跃**一律纯文本处理，不得设任何真实门槛**。否则又是第二个"等一年"。

## B.4 前情回收：记痕机制（`rec.marks`）

### B.4.1 需求

终章《停手》里，它说的难听的话，**全是前面章节里玩家自己说过的**。

### B.4.2 设计（**一级完整 key，扁平集合**）

> **⚠️ v163 定稿：一级完整 key，不是两级槽位。** 初稿写的是「外层槽 `c4` → 内层 token `notbright`」两级；剧本 `v163-主线剧本-沁灵纪.md` §5 主张压平为一层，团队已裁定采纳。**本节与剧本同步，引擎写 `rec.marks[值] = 1`（扁平）。**

```
rec.marks = {
  "c2_forgot":    1,       // 第 2 章，玩家选了「……我确实不记得了」
  "c4_greedy":    1,       // 第 4 章，玩家说了「不是。是我贪心」
  "c5_mindown":   1,       // 第 5 章，玩家说「别多管闲事。睡吧」
  "c7_hide":      1,       // 第 7 章，玩家把串藏起来
  "c9_unneeded":  1,       // 第 9 章，玩家说「你不需要我了」
  "ch6_entry":  "idle"     // 非记痕 key：第 6 章版本锁定（与记痕同住，靠前缀区分）
}
```

- **`mark` 的值 = 全局唯一完整 key**（形如 `cN_token`，如 `c4_greedy`）—— **不是槽 `c4`**。同一章的不同选项**必须映射到不同的值**，否则「三选一」被压成同一个值，终章回扣三选一都还同一句，玩家「我选了什么」白选。
- **剧本侧**：每个可被引用的选项带一个 `mark` 字段。现有选项结构是 `{t, go, tone}`（:2390 等），**加一个 `mark` 即可，向后兼容**（缺失 = 不记账）。
- **台词侧**：一张 `SAID_LINES` 表，`mark 完整 key → 一句话`。终章用 `{said1}{said2}{said3}` 注入，取 `rec.marks` 里**章序最早的三条**。
- **为什么存 key 不存整句**：100 只串 × 5 句 × 30 字 = 15KB；存 key 只有 **~150 字节/只，全库 15KB → 1.5KB**。差 10 倍，且 key 不会因文案改动作废。

> **为什么一级优于两级**（团队裁定，三条理由）：
> ① `rec.marks` 里本来就要放 `ch6_entry` 这类**非记痕** key，扁平更一致；
> ② 一级 key 下 `SAID_LINES[mark值]` **直接命中**，没有「槽对了、token 写错」的静默回落（这类 bug 只在终章才暴露，最难查）；
> ③ 记痕册 7 格只需按前缀过滤计数，不必再维护槽位。

### B.4.3 记账点（**7 章 · 8 处节点 · 19 个值 key · 20 次出现**）

| 章 | 写 mark 的节点 | `mark` 值 key（一级完整 key） | 终章怎么用 |

**7 章 / 8 处节点 / 19 个值 key / 20 次出现**（`SAID_LINES` 表恰好 19 条，一一对应、无缺无余）。
> ⚠️ **第 6 章两版不能共用一个槽**：初稿想「原生版与兜底版共用 `c6`」，会在终章**注入一句玩家从没说过的话**——兜底版的三个选项（`c6b_*`）与原版的（`c6_*`）完全不同，必须另立三句。
> 第 6 / 6b 由 `rec.marks.ch6_entry`（值 `"idle"` / `"days"`）**二选一进入，同一只串只会走一版**，不冲突；它与记痕 key 前缀不同，靠正则区分。

> **兜底（必做）**：玩家跳章 / 全选默认 / 老存档 → `rec.marks` 可能为空。
> 终章取 mark 时**必须走 fallback**，且**不能再用短 key `c4`（已不存在）**：
> ```js
> const keys = Object.keys(rec.marks).filter(k => /^c\d+[a-z]?_/.test(k)).sort();
> const line = SAID_LINES[keys[0]] || DEFAULT_SAID_POOL[hash(item.id) % 4];
> ```
> 即「**取出全部记痕 key → 按章序排序 → 取最早 1 条**」再查 `SAID_LINES`；取不足时走 `DEFAULT_SAID_POOL`（4 条，风格一致，玩家不会察觉穿帮）。

> 🔴 **过滤正则必须写成 `/^c\d+[a-z]?_/`，不能写成 `/^c\d+_/`。**
> 后者**匹配不到 `c6b_here`**（第 6 章兜底版的三个 mark，`c6b` 中夹了一个字母）—— 走了兜底版第 6 章的玩家，3 条记痕会对终章回扣**隐形**。这是真 bug，必须先在此定稿。

**规则：**
- **第 2 章埋的时候只给名词 + 一句模糊的话**（"那天你把它放在窗台，后来就没再见过"），**不解释、不点破这是伏笔**。揭晓留到第 10 章。
- 埋点是一句**通用台词 + `{物核}` 注入**（通用于全部 6 选 1），文案**不用写 6 遍**。
- **未答 / 自填为空 → 回落默认值「一把旧钥匙」**（6 条里情感最强的一条）。
- 自填入口保留（限 8 字、空值回落），**不做敏感词过滤**（过度处理会打断情绪）。

### B.4.5 选项 → 反馈闭环（每个分支点必须回答"玩家凭什么知道自己选了什么"）

| 反馈层 | 形式 | 时机 | 成本 |
|---|---|---|---|
| **即时 · 文本** | 它当场接一句（每个选项必须有**不同的**下一句，禁止三选一同剧情） | 选完立刻 | 0 |
| **即时 · 语气** | `tone`（warm/cool/fun）累加 → 影响本幕的自动收尾分支 | 选完立刻 | 0 |
| **即时 · 记账** | 记痕册对应格子**亮起来**，并显示那句话 | 选完立刻（**这是最关键的反馈**） | 0 |
| **延迟 · 回响** | 后面章节里它提起这句话 | 几章之后 | 0 |
| **延迟 · 终章** | 它还给你 | 第 12 章 | 0 |
| **延迟 · 数值** | 部分选项 ±bond（`addBond(rec, ±2)`，已有函数） | 选完立刻 | 0 |

> ⚠️ **纪律**：第 3 项（记痕格子亮起来）是**强制项**。
> 一个选项如果没有可见的即时反馈，等于没做。现有 `chapWalk` 只写 `tone`，**玩家选完什么都看不到**——这是当前最大的可玩性欠账，必须在这次一起补掉。

# 【C】CG 触发与收集规则

## C.1 触发时机：**聊完这一章、停在章末结尾画面时弹确认**（不是中途弹）

沿用现有 `confirmModal`（app.js:393）。

**结论：章末弹，不在中途弹。** 五条理由：

| # | 理由 |
|---|---|
| 1 | **中途弹会打断对话沉浸**——这是"当小说看"的第一杀手。章末弹时玩家刚读完一段完整情绪，此刻"想要一张画留住它"的欲望最强，**转化率最高**。 |
| 2 | **章末弹可复用章末收尾 UI**（题词 + 按钮），不需要新弹层组件，实现成本最低。 |
| 3 | **技术风险**：`chapWalk` / `thWalk` 是**同步 while 循环**（:4677 / :3362）。中途 `await` 出图会打断状态机，且玩家中途退出会留下半截 `node`。章末弹时 `t.ended === true`，状态已落定，**最安全**。 |
| 4 | 文案策划给的 CG 题词（「灯还亮着，你把我翻了个面。」）本身就是**章末余味**，跟章末画面是同一件事。 |
| 5 | 中途弹会出现"玩家还没看完就开始考虑要不要花钱"——**把消费决策插进情绪里，是体验事故**。 |

**补充规则：**
- 🔴 **只对「有效主串集」内（`mainSet`）的串触发**（见 C.2）。集外的串章末**只显示题词文字**，不弹确认、不出图。
- **"每章只弹一次"是按【串 × 章】计，不是按章计**。改集合制后，N 只主串**各自维护自己的 8 章弹窗状态**：主串 A 的 CG-05 弹过一次，不影响主串 B 的 CG-05 该弹。
  → 存储落在各自的 `rec.cgs[ch]` 上（key 已含串 id，天然隔离），**不需要额外的"已弹过"字段**。
- 玩家选"以后再说"后，CG 以**剪影 + 「画一张」按钮**常驻在章末页与相册里，随时回来补。
- 多主串时，弹窗**必须点明是哪一只**（否则玩家不知道自己在给谁花钱）：
  > 「要为**「XXX」**的这一章画一张插画吗？」
  > 「横版一张，约 ¥0.13。画好会存进相册，不用重画。」
  > `[ 画一张 ]` `[ 以后再说 ]`
  （尺寸按当前出图通道的实际输出，**不在文案里硬编码 px**，避免与两档规格 `CG_MAIN_SIZE`=512 / `CG_THUMB_SIZE`=384 脱节）
- **CG-01（第 1 章）不例外，同样章末弹。** 第 1 章只有 12-16 条，1 分钟就读完，没必要开例外口子。

## C.2 主串：**有效主串集**（v163 改版 · 集合制）

> **改版依据（用户原话）**：「主串 1 个有点少不规定数量，让我自己选吧，或者就是我在列表里面评分达到 5 星的串」
> **结论**：主串从**全局单值**改为**集合**。数量**不限**。CG 仍只对**集合内**的串生成。

### C.2.0 有效主串集：两个来源 + 一条兜底

```
有效主串集 mainSet = 去重( 手动勾选 ∪ 5 星自动纳入 )  ；若结果为空 → 兜底取「开沁最早那只」
```

| 来源 | 规则 | 开关 |
|---|---|---|
| **A · 手动** | 玩家在「沁灵纪」页勾选。**任意数量，不限个数**（1 只也行，全选也行） | 始终生效 |
| **B · 自动** | 列表里 `(Number(item.star) \|\| 0) >= 5` 的串**自动纳入** | `ww_story.mainStar5`，**默认 true** |
| **兜底** | `mainIds` 空 **且** 无 5 星串 **且** `mainStar5` 关 → 取**开沁最早那只**（沿用原 `threadRank` 逻辑） | 自动 |

**⚠️ B 源用 `>= 5` 而不是 `=== 5`**：与现有实现保持一致 —— `app.js:315` 的 `itemStars()` 已把值钳在 `0..5`，`app.js:1075` 与 `:6830` 的「5 星自动进喜欢展柜」用的都是 `(Number(i.star) || 0) >= 5`。**复用同一判式，不引入第二套语义。**
**⚠️ 不新建字段、不新建评分 UI**：`item.star` 已存在（`app.js:337` 写入），列表页已有星级控件（`app.js:319`）。

### C.2.1 存储：全局一条，不进 `rec`

```js
// localStorage: ww_story
{
  mainIds:  ["<itemId>", ...],   // 手动勾选集合（不限数量）；默认 []
  mainStar5: true,               // 是否启用「5 星自动纳入」；默认 true
  mainAt:   <ts>,                // 最近一次改动时间
  switched: 0,                   // 改动次数（用于文案升级，不硬限）
  wuhe:     "一把旧钥匙"          // 物核（全局量，全书只问一次，见 B.4.4）
}
```

**为什么不进 `rec`**：主串是**全局概念**。存进 `rec` 要维护 100 个 `isMain` 的一致性；存全局一条，勾选只改一处。
**旧值兼容（只读，不双写）**：老存档若有单值 `mainId`，读取时折算 ——
`mainIds = Array.isArray(w.mainIds) ? w.mainIds : (w.mainId ? [w.mainId] : [])`
⚠️ **不双写**：写入路径只写 `mainIds`，`mainId` 一旦被读出来就**不再回存**（避免两处状态打架）。

> 🔴 **实测：上面这条兼容行「无数据可兼容」，纯防御（1 行，留着无害）。**
> 全项目 grep `ww_story` 只出现 **2 次，都是读**（`storyMainId()` 里的 `localStorage.getItem("ww_story")`），**没有任何 `setItem("ww_story", …)` 写路径**。推论（硬结论）：
> - **没有用户的设备里存在 `mainId`** → `storyMainId()` **恒返回 `""`** → 现有 `isMain`（`:3425`）与 `isMainIn`（`:3684`）**恒为 false**（若有剧本写了 `when:{isMain:true}`，**当前永不触发**）；
> - 所以本改版**在行为上是"纯新增"，不是"修改线上行为"**——**无需设计任何迁移 / 回填**；
> - 兼容行保留，防的是"**将来**若有别的入口写了 `mainId`"。

### C.2.2 实现签名（架构师照此落地）

```js
// 唯一入口：算出「有效主串集」。O(n) 一次扫描，全程 Set 操作。
// items: 全部宝贝（DB.getAll 结果）  store: Spirits.load() 结果
function mainSetOf(items, store) -> Set<string>   // 元素为 String(item.id)
```

**计算顺序（必须按此序，否则兜底会误触发）：**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | `const s = new Set()` | |
| 2 | `ww_story.mainIds` 里**仍存在的** id 全进 `s` | **必须剔掉已删除的串**，否则主串集会有幽灵 id |
| 3 | 若 `ww_story.mainStar5 !== false` → 遍历 `items`，`(Number(it.star)||0) >= 5` 且 `!it.gifted` → 进 `s` | **`!it.gifted` 见 D3**：已送人的串天数是冻结的，纳入无意义 |
| 4 | `if (s.size === 0)` → `s.add(threadRank(items, store)[0].id)` | **兜底**，见下 |
| 5 | `return s` | |

> 🔴 **第 4 步的兜底是最关键的一条（防死锁）**：新用户一进来 `mainIds` 是空的、也没有 5 星串——**若没这一步，主线会全局锁死，没有任何一只串能推进**。
> **准确措辞**：`mainIds` 为空 **且** 无 5 星串 **且** `mainStar5` 关闭时，回退「**开沁（`bornAt`）最早的那只**」；排序复用 `threadRank`（:3077）的同一套规则（`bornAt || createdAt` 升序、`id` 兜底），取 `ranked[0]`。

**"已定设定"不在 `mainSetOf` 里过滤**：它只影响**出图**，不影响**能不能进主串集**（玩家勾了就该在主串列表里看到它）。过滤放在 CG 环节，见 D5。

> 🔴 **这是「改造」不是「新增」——代码已有单值实现，别照着从零写。**
> 现有 `storyMainId()`（`spirits.js:3393-3399`）读 **`ww_story.mainId`（单值）**，注释就写着「设计 §C.2：ww_story 全局一条，不进 rec」。`mainSetOf()` **取代**它：
> - 调用点：`const mainId = storyMainId()` → `const mainSet = mainSetOf(items, store)`；
> - `soloEnv.isMain`（**现 :3425**，单值比较 `String(item.id) === mainId`）→ `mainSet.has(item.id)`；
> - `thEnv.isMainIn`（**现 :3684**，单值比较）→ `mainSet.has(m.id)`。
> **`storyMainId` 及其导出（:5684）需一并处理**（替换或保留为 `mainSetOf` 的兜底分支）。

### C.2.3 `isMain` / `isMainIn` 的最终判定

| env | 字段 | 判定式 | 说明 |
|---|---|---|---|
| `soloEnv`（单串） | `isMain` | `env.mainSet.has(item.id)` | **Set 成员判定**（现有实现 `:3425` 是单值 `String(item.id) === mainId`，**改这一行**） |
| `thEnv`（会话） | `isMainIn` | `ms.some(m => env.mainSet.has(m.id))` | **会话内任一只**在主串集里即为 true（现有实现 `:3684` 为单值比较） |

`mainSet` 由 `mainSetOf()` 算**一次**，随 env 一起下传；两个 env 共用同一个 `Set`，不重复计算。

### C.2.4 勾选与改动规则

| 规则 | 内容 |
|---|---|
| **数量** | **不限**。1 只 / 5 只 / 全选都可以。UI 给"全选 / 全不选"两个快捷按钮即可（不要设上限，用户明确说"不规定数量"） |
| **入口** | 「沁灵纪」页顶部（手动勾选 + `mainStar5` 开关） |

| **旧 CG 处置** | **不删**。取消勾选的那只，`rec.cgs` 原样保留，相册里标「**旧主 · XXX**」（或"未启用的主串"）。重新勾回来时**直接复用**，不重画 |
| **次数** | **不硬限**。`switched >= 1` 后确认文案升级（提示已改动 N 次，每次新增主串都要多出 8 张） |

### C.2.5 成本提示：必须写总量（不能只写单只）

**N 只主串 = N × 8 张 CG。** 单张约 ¥0.13。确认弹窗要按**新增的主串数**算总量：

> 「这次要启用 **N** 只主串，共 **N×8** 张 CG，约 **¥{N×8×0.13}**。」
> 例：勾 1 只 → 「共 8 张，约 ¥1.04」；勾 3 只 → 「共 24 张，约 ¥3.12」

⚠️ **只对"新增"的主串算钱**：已经在主串集里、且 `rec.cgs` 已齐的串**不重复计费**（重勾回来直接复用，`key` 匹配即命中缓存）。
⚠️ **每张仍须「确认才画」**（沿用 C.1 的章末 `confirmModal`），**不做批量自动出图**——钱是用户的。

### C.2.6 相册数据接口（UI 表达交给 UI 美术）

**多主串天然支持，不需要新结构**，因为：

- `rec.cgs` **本来就是每串一份**（挂在各自 `rec` 上）
- 收集度分母 `CG_TOTAL = 8` 也是**按 `rec` 算**的

**所以只需这一个接口约定：相册按 `ownerId` 分组。**

```js
// 相册数据：主串集内每只各出一组
albumGroups(items, store) -> [
  { ownerId: "<itemId>", name: "XXX", cgs: [ {key, at, chapter, title, hasFigure}, ... ], got: 3, total: 8, isMain: true }
  , ...                                          // 每只主串一项
  // 若 rec.cgs 里有 key 但该只已不在主串集 → isMain: false（「旧主」分组）
]
```

- **归组依据**：`rec.cgs` 所属的串（即 `rec` 的 key）。
- **`isMain`**（**复用现有 when 键名，不新造 `isActive`**）：该只是否**当前在**有效主串集里（= `mainSet.has(ownerId)`）。`false` → 归入「旧主」，**已收集的图不删、不掉计数**。
  > ⚠️ **命名纪律**：`isMain` / `isMainIn` **是已存在的 when 键**（`spirits.js:3523` / `:3684`，**剧本作者已经在用**）。同一个概念**不要再造第三个词**——相册只需要一个布尔：「这只现在还算不算主串」。字段名不影响实现，但三个名字并存，后人必踩。
- **收集度是"每只各算 N/8"**，**不做跨串总收集度**（跨串求总会出现"这只 3 张 + 那只 5 张 = 8/8"的假满，是错的）。
- **像素仍在 IndexedDB `ww_cg`**，key 已含串 id（见 C.3 缓存 key），天然不冲突。

### C.2.7 主串 / 非主串的差别

| | 主串集内（N 只） | 其余（100-N 只） |
|---|---|---|
| 12 章主线剧本 | ✅ 全量 | ✅ 全量（**剧情不打折**） |
| CG | ✅ **每只各 8 张**（玩家确认才出图） | ❌ 不出图，章末只显示题词文字 |
| 记痕册 | ✅ | ✅ |
| 日记 / 问候 / 回响 | ✅ | ✅ |
| `lingxiTalk.log` | ✅ 全留 | ❌ 不留（只留 `done/ending/marks`，见 §4） |

> **关键不变**：非主串**只是不出图，剧情一点不少**。
> 改集合并不会让成本失控——**成本由"玩家勾了几只"决定，是玩家自己按的按钮**；且每张都要单独确认。默认只需 1 只（开沁最早那只）时，成本与改版前完全一致。

## C.3 缓存与失效规则

### 存储结构：**像素走 IndexedDB，元数据走主 store**（已拍板）

localStorage ww_spirits : rec.cgs = {              → 只存元数据
  "cg01": { key, at, chapter, title, provider, hasFigure },
  ...
}
```

**关键规则：**
- **收集判定以元数据为准**。相册数「已收 N/8」只看 `rec.cgs` 有几个 key 匹配——**不依赖 IndexedDB 是否真的读得到像素**。
  → 好处：IndexedDB 被清（浏览器回收 / 换机）时，**收集度不会掉**，只是点开那张图时显示"图丢了，要不要重画"。
- **主 store 里不再放像素**，`pruneForQuota` 的压力直接消失（8 张 CG 对 localStorage 的占用从 **~1 MB 降到 ~2 KB**，只剩 8 条元数据）。
- **主线 CG 规格 = 512px / q0.72（`CG_MAIN_SIZE`，app.js:2754）、缩略图 384px（`CG_THUMB_SIZE`，:2756）—— 两条路径同尺寸**，差别只在**存哪**：主路径进 IndexedDB `ww_cg`；IndexedDB 不可用时（隐私模式 / 老浏览器 / 配额极小的机型）像素写**独立 key `ww_cg_px`**（spirits.js:97，`pruneForQuota` 够不着它）。
  - IndexedDB 解决"存不下"；`pruneForQuota` 顺序改造只作用于回落路径的**丢弃顺序**。
  - ⚠️ **`CG_IMG_SIZE = 768`（app.js:2700）只服务 v125 的单张突破 CG，主线一行不用它**——别把 768 当主线规格。
- **跨手机同步**：`ww_spirits` 整库一行 JSON **天然带不走像素**（这是好事，否则同步体积会爆）。新机首次打开相册 → 元数据显示 N/8，点开某张提示"「画一张」把这张补回来"。
  ⚠️ 这与"重看永不重画"不冲突：**同一台机器上永不重画**；换机后的补画是**用户主动点**的，且必须走 `confirmModal` 告知要花钱。
- 现有的 `rec.cgUrl / rec.cgAt / rec.cgStage / rec.cgKey` **保留不动**（v125 的突破 CG 仍走它），两者互不干扰。

### 缓存 key

```
key(串, 章) = 串id + "|" + 章节构图ID + "|" + variant + "|" + appearanceSeed + "|" + gender + "|" + provider
```

- 🔴 **`串id` 必须进 key（集合制后新增，最容易被漏掉的一条）**：`ww_cg` 是**一个共享的 IndexedDB store**，N 只主串的像素都往同一个库里放。若 key 里没有串 id，两只会撞 key、**后者直接覆盖前者**。
  ⚠️ 而且这是**真实会发生**的：`appearanceSeed` 未设置时默认 `0`（很多串都不带这个字段），仅靠它不足以区分 owner。
  → 相册按 `ownerId` 分组（C.2.6）也依赖这一点，两者是同一件事的两面。
- **章节构图 ID 不进 key**（CG-01 永远是「开沁之夜」那个构图，不会变）。
- 沿用现有 `cgKeyOf` 的四个锚点（:3335），**改动是两处**：① **前面加串 id**；② `stage` 换成章节 ID。
- ⚠️ 现有 v125 突破 CG 用的 `rec.cgUrl/cgKey` **保持原样**（单串单张、存 `rec` 里、不进 `ww_cg`），**只在 `rec.cgs` 路径上加串 id**，不要混改。

### 🔴 配额：8 张 CG 的体积账（**尺寸只有两档：主线 512 / 缩略图 384**）

- **主路径 = IndexedDB `ww_cg`**：像素不在 localStorage，5MB 约束消失，收集判定以元数据为准。
- **回落路径 = IndexedDB 不可用 → 独立 key `ww_cg_px`**（spirits.js:97）：**同尺寸 512/q0.72**，只换存储位置。
- **改造 `pruneForQuota`（:84）必做**：把 CG 从"第一个丢"改成"**最后一个丢**"，从旧到新丢，**保底留最新 3 张**（`CG_THUMB_KEEP=3`，spirits.js:99；`dropOldCgThumbs` 收 `rec`，**天然按串各算、不跨串比较**，无需改造）。现有顺序是 `cgUrl` 第一个被清 → 8 张会**整体消失**、玩家白花钱。**只作用于回落路径的丢弃顺序**。

## C.4 收集度

| 项 | 算法 | 显示 |
|---|---|---|
| **主线 CG** | 🔴 **每只主串各算 `N / 8`**（**以该只的 `rec.cgs` 元数据判定**，不看像素在不在） | 相册该只分组标题：「已收 3 / 8」 |
| **记痕** | 每只 `N / 7`（该只 `rec.marks` 里已记的 key 数） | 记痕册标题：「它记住了你说的 4 句话」 |
| **节令限定 CG** | 单列（`M / 当季总数`） | **不混入主线 8 张**，避免"永远集不满"的挫败 |
| **未解锁** | 剪影 + 章名灰显 | 保留收集欲（文案策划 §5.1-6 已提） |
| **未解锁格的提示文案** | 🔴 **「读完第 N 章解锁」（具体门槛，不用"还没到时候"通用句）**。`N` 由**引擎按 `CG_NEED` 常量表由 CG→章节推导**：`CG-01→1 / 02→3 / 03→5 / 04→7 / 05→9 / 06→10 / 07→11 / 08→12`，常量表与 `CG_STATE_HINT` 同处落库 | ⚠️ **`need` 不是剧本字段**（剧本 §0 的 `cg` 是**纯字符串** `cg: "CG-01"`，不要求文案侧提供门槛）。`CG_STATE_HINT.locked` 的「还没到时候」**退化为纯兜底**——仅当常量表推导不到章节时才用 |

> **不用百分比**：8 是个整数，「已收 3 / 8」比「37.5%」有质感。中式器物的计数就该是「三件 / 八件」。
> **收集度只增不减**：因为判定基于元数据，像素丢失（换机 / IndexedDB 被回收）**不会掉收集度**——这直接保住了玩家的成就感。
> 🔴 **绝不做"跨串总收集度"**（集合制改版后新增的纪律）：分母 `8` 是**按串**的，跨串求总会出现 **"主串 A 拿 3 张 + 主串 B 拿 5 张 = 8/8 已满"** —— 这是**假满**，且会让"逐只 8 章"的叙事结构彻底失效。
> 若要给玩家一个全局感，用**「N 只主串，共收 M 张」**（M = 各只之和，不做分母），或**每只一行进度**（C.2.6 的 `albumGroups` 天然就是这个形状）。

**建议分级裁剪（进 `pruneForQuota`）—— 判据是"是否在有效主串集内"：**

| 字段 | 是否进 prune | 依据 |
|---|---|---|

| `ww_story`（`mainIds` / `mainStar5` / `wuhe`） | ❌ **不进** | **全局小数组**，100 只全勾也才 ~2.5 KB，裁它没有收益、还会丢玩家勾选 |
| `rec.cgs` | ❌ **不进**（只留元数据，像素在 IndexedDB） | 元数据 N×250 B 量级可忽略；**丢了会掉收集度**，绝不能裁 |

## C+.1 进阶四阶段（头身比随阶段变）

### C+.1.1 设计原则

| # | 原则 | 理由 |
|---|------|------|
| **P1** | **阶段由「挂瓷后天数 ∧ 盘玩次数」双条件派生，取较慢者；旧 `rec.stage` 值忽略，不再依赖手动突破** | 用户原话："时间(挂瓷后天数) 和 盘玩次数 都是衡量条件：盘得少就到不了好状态"。单一 growth 量（旧 `plays*3+days`）会让"只挂机不盘"的串照样长，必须拆成两个独立闸门 |
| **P2** | **复用同一变量 `rec.stage(1-4)`，不改字段名、不碰 `ww_spirits` 这个 key** | 上方【B】全部 `when:{stage:N}`、`needCg(stage>=3)`、`stageDef(rec.stage)` 读者继续生效，**零改造兼容**。只改"stage 怎么算出来" |
| **P3** | **阶段 = 头身比阶梯**：初生 4 头身 / 少年 6 头身 / 成年 8 头身 / 完成体 9 头身（更华丽服饰+场景） | 用户原话头身比 4 / 6 / 8-9 / 完成体 |
| **P4** | **完成体要容易达成**（否则用户坚持不到）；建议挂瓷后 ~1 月→成年、~4 月→完成体（上限不超过半年） | 用户原话"完成体别太难达成（否则用户坚持不到）" |

### C+.1.2 数值模型（天数下限 ∧ 盘玩次数下限 · 取双条件中较慢达成者）

> **判定语义**：到达第 N 阶，**必须 `days ≥ STAGE_DAYS[N]` 且 `plays ≥ STAGE_PLAYS[N]` 同时成立**。
> 任一不满足 → 停在当前阶。即"盘得少就到不了好状态"；只有"既挂得久又盘得勤"才长。

| 阶段 | 名称 | 头身比 | 挂瓷后**天数下限** `STAGE_DAYS` | **盘玩次数下限** `STAGE_PLAYS` | 触发含义 |
|---|---|---|---|---|---|
| 1 | **初生**（幼年期） | 4 头身 | 0 | 0 | **挂瓷即初生**（自动） |
| 2 | **少年**（成长期） | 6 头身 | **7** | **5** | 约 1–2 周（盘过 5 次） |
| 3 | **成年**（成年期） | 8 头身 | **30** | **20** | 约 1 个月（盘过 20 次） |
| 4 | **完成体** | 9 头身（更华丽） | **120** | **60** | 约 **4 个月**（盘过 60 次） |

**三档玩家实测落地（对照 B.1.1 的 A/B/C 型）：**

| 型 | 特征 | 少年 | 成年 | 完成体 |
|---|---|---|---|---|
| A 日活轻度（1 盘/天） | plays≈days | 第 7 天 | 第 30 天 | 第 120 天（**4 个月**） |
| B 日活重度（3 盘/天） | plays≫days | 第 7 天 | 第 30 天 | 第 120 天（days 卡瓶颈） |
| C 佛系（1/3 天开+盘） | plays≈days/3 | 第 15 天 | 第 60 天 | 第 180 天（**6 个月**，仍 ≤ 半年上限） |
| **零盘玩家**（只开不盘） | plays=0 | **永不** | **永不** | **永不**（正确：盘得少就到不了） |

→ **完成体对"至少偶尔盘"的用户 4–6 个月可达**，达成成本低；真正从不盘玩的串永远停在初生——正是设计意图。

**阈值可调旋钮**：`STAGE_DAYS` / `STAGE_PLAYS` 集中配置（见 C+.1.3）。若上线后留存数据表明掉队，优先下调 `STAGE_PLAYS`（盘玩门槛）而非天数门槛。

### C+.1.3 判定函数（供架构师实现，全部 O(1) 单串）

```js
// 阈值集中配置（替换旧 STAGES.need 的"成长值"语义；STAGES 仅保留 name/icon/look/sizeZh）
const STAGE_DAYS  = [0,   7,  30, 120];   // 1-based；[0] 占位
const STAGE_PLAYS = [0,   5,  20,  60];
const HEAD_COUNT  = [0,   4,   6,   8,   9]; // 头身比（完成体取 8-9 上沿）

// 阶段：双条件取较慢者（阈值单调，故任一不满足即 break）
function stageOf(item, rec, now) {
  const days  = dayNoOf(rec && rec.bornAt, now);   // 挂瓷后自然日；未挂瓷 = 0（dayNoOf 已核实 :3320）
  const plays = Number(item && item.playCount) || 0;
  let s = 1;
  for (let k = 2; k <= 4; k++) {
    if (days >= STAGE_DAYS[k] && plays >= STAGE_PLAYS[k]) s = k;
    else break;                                     // 取较慢者：任一不满足即停
  }
  return s;
}

// 头身比映射（UI / 架构 / 文案统一引用）
function headCountOf(stage) { return HEAD_COUNT[Math.min(4, Math.max(1, Number(stage) || 1))]; }
function stageOrnate(stage) { return Number(stage) === 4; }   // 完成体：更华丽服饰 + 场景

// 进度（双轴都满才 100%；UI 反馈用）
function stageProgress(item, rec, now) {
  const s = stageOf(item, rec, now);
  if (s >= 4) return { isMax: true, pct: 100 };
  const dNeed = STAGE_DAYS[s + 1], pNeed = STAGE_PLAYS[s + 1];
  const days = dayNoOf(rec && rec.bornAt, now), plays = Number(item && item.playCount) || 0;
  const dRem = Math.max(0, dNeed - days), pRem = Math.max(0, pNeed - plays);
  const pct  = Math.min(100, Math.round(days / dNeed * 100), Math.round(plays / pNeed * 100));
  return { pct, toNextDays: dRem, toNextPlays: pRem, bottleneck: dRem >= pRem ? "days" : "plays" };
}
```

  const out = [];
  items.forEach(it => {
    const rec = store[it.id] || {};
    (rec.events || []).forEach(e => out.push({ ...e, ownerId: it.id, ownerName: it.name }));
  });
  out.sort((a, b) => b.at - a.at);           // 倒序：最近的在前
  return out;
}
```
- **无分母**：回顾是开放日志，不像 CG 有 `CG_TOTAL`；只显示"共 N 件纪事"。
- **渲染**：时间线列表，每张卡 `icon + 日期 + 标题 + summary`；`linked` 里非本人的沁灵名可点 → 跳该沁灵详情。
- **绝不两两枚举**：100 只的纪事是各自 `rec.events` 拼起来，不存在"两只之间比对"的 O(n²)。

### C+.2.6 CG 汇总入口（已收集 + 未收集占位，分母 `CG_TOTAL`）

> 与上方 C.2.6 / C.4 对齐，**不重复造轮子**——只定"入口位置"以服务导航收敛。

- **分母**：`CG_TOTAL = 8`（按**每只主串各算**，C.4 纪律：**绝不做跨串总收集度**）。
- **已收集**：显示缩略图（`CG_THUMB_SIZE`=384，app.js:2756）；**未收集**：剪影 + 「读完第 N 章解锁」（具体门槛，不用"还没到时候"通用句，见 C.4 的 `CG_NEED`/`CG_STATE_HINT`）。
- **入口**：
  1. 每只沁灵详情页（现有 `albumGroups` 按 `ownerId` 分组，C.2.6 已建）；
  2. 沁灵巷 `#/town` 新增「全主串 CG 墙」（汇总所有主串，每只一行「已收 X / 8」+ 缩略图宫格），与纪事墙并列。
- **像素丢失不降收集度**：判定以 `rec.cgs` 元数据为准（C.3），回顾/CG 墙显示 N/8 不会因换机掉数。

## C+.3 夜话打字节奏

### C+.3.1 现状（已核实）

`renderTalkPage` 的 `step()`（`app.js:5058-5063`）当前是**整条气泡延迟**，**非逐字**：
```js
timer = setTimeout(() => { pend.innerHTML=""; append(m); scrollEnd(); step(); },
  380 + Math.min(900, String(m.text||"").length * 24));   // 整泡延迟，最长 1280ms
```
问题：气泡"啪"一下整段出现，缺少打字过程，沉浸感弱。

### C+.3.2 建议值与落点（比当前慢一档 · 保证沉浸）

- **新增常量**：`TALK_CHAR_MS = 45`（每字间隔 ms，可调 35–55）；`TALK_LEAD_MS = 300`（打字前"思考气泡"停留）。
- **改写 `step()` 的整泡延迟 → 逐字揭示**（覆盖夜话 + 主线两端，因 `renderChapTalkPage` 复用 `renderTalkPage`，:5106）：
  ```js
  // 原整泡延迟替换为：先显示打字点 TALK_LEAD_MS，再逐字揭示
  pend.innerHTML = '<div class="nt-row"><div class="nt-av"></div><div class="nt-bub nt-typing"><i></i><i></i><i></i></div></div>';
  scrollEnd();
  timer = setTimeout(() => {
    const full = String(m.text || "");
    let i = 0;
    const tick = () => {
      i++;
      pend.querySelector(".nt-typing") && (pend.innerHTML = msgHtml({ ...m, text: full.slice(0, i) }));
      // 超长句（>80 字）每拍多吐 2 字，避免过久
      if (i < full.length) { if (full.length > 80 && i < full.length - 1) i++; timer = setTimeout(tick, TALK_CHAR_MS); }
      else { pend.innerHTML = ""; append(m); scrollEnd(); step(); }
    };
    tick();
  }, TALK_LEAD_MS);
  ```
- **保留"点一下跳过打字"**（:5075 的 `body` 点击 → 一次性把所有 pending 字补完 + `showFoot()`）——用户不耐烦时可秒过，不牺牲沉浸也不牺牲效率。
- **效果对照**：30 字气泡，原 1280ms 一次性；现 300 前导 + 30×45≈1350ms 渐进，**总时长相近但"在打字"可见**，沉浸感"慢一档"。

### C+.3.3 边界

- 只改 `step()` 内 `setTimeout` 块（:5058-5063），**不动** `paint`/`append`/`showFoot`/`pick` 等其他逻辑。
- 主线对话（沁灵纪）与夜话共用此壳，一次改写两端生效。
