## 0.3 🔴🔴 P0：`化形`（stage 4）当前**永远无法达到**（r2 读码发现）

### 现象

`spirits.js:725-726`：
```js
const STAGE_DAYS  = [0,   7,  30, 120];   // 1-based；[0] 占位
const STAGE_PLAYS = [0,   5,  20,  60];
```
`spirits.js:732-735` 按**阶段号**直接索引：
```js
for (let k = 2; k <= 4; k++) {
  if (days >= STAGE_DAYS[k] && plays >= STAGE_PLAYS[k]) s = k;
  else break;
}
```

### 实测（脚本复算，非推测）

| 阶段 | **应为**（按注释「1-based、[0]占位」） | **当前实际** |
|---|---|---|
| 开窍 stage 2 | 7 天 + 5 次 | **30 天 + 20 次** ❌ 错位 |
| 蜕形 stage 3 | 30 天 + 20 次 | **120 天 + 60 次** ❌ 错位 |
| **化形 stage 4** | **120 天 + 60 次** | **`STAGE_DAYS[4]` = `undefined`** → `days >= undefined` 恒 false → **永远达不到** 🔴 |

### 铁证：同文件 `HEAD_COUNT` 是**正确**写法

```js
const HEAD_COUNT = [0, 4, 6, 8, 9];    // 长度 5，按 stage 直接索引 ✅
function headCountOf(stage) { return HEAD_COUNT[Math.min(4, Math.max(1, stage))]; }
```
`HEAD_COUNT` 长度 **5**（含 `[0]` 占位）→ 证明本文件的既定约定就是**「数组长度 5、按阶段号索引」**。而 `STAGE_DAYS`/`STAGE_PLAYS` 只有 **4** 位 → **少一位，整体错位**。

### 修法（改 2 行）

```js
const STAGE_DAYS  = [0, 0,   7,  30, 120];   // 补 [1]=0（凝形即起点）
const STAGE_PLAYS = [0, 0,   5,  20,  60];
```
> ⚠️ **必须补「前导占位」，不能补「后一位」。** 补后一位会把开窍从 30 天砍到 7 天（顺带改了 index 2/3 的语义）。本文件 §4.2 的整张解锁表、以及文案 v4 §3.1 都**已按 `[0,0,7,30,120]` 读数写完**，所以这两个数组本来就该有前导 0。
> ✅ **文案策划已独立复现并验证**：挂瓷 3000 天 / 盘玩 999 次仍停在 stage 3；跑 **8241 个样本，掉级 0 例**（`stageOf` 是纯函数，两门槛都只变松，已达成阶段不可能掉）→ **对现有玩家是纯增益**。
> 另需**顺带核对** `stageInfo`（`:1148`）与 `stageProgress`（`:743`）——它们用 `STAGE_DAYS[cur + 1]`，补位后语义才与 `stageOf` 一致（当前两者口径也是错的）。

### 🔴 为什么这条比我这份设计更要紧

| 受影响的东西 | 后果 |
|---|---|
| **本设计的恋爱线**（锁 `stage ≥ 4`） | 🔴 **永久锁死**——玩家永远看不到任何恋爱内容 |
| **v163 主线第 10/11/12 章**（`stage≥4` 门槛） | 🔴 **主线永久断在第 9 章** |
| `stageInfo` / `stageProgress` 的 `dNeed/pNeed` | UI 进度条分母错位（"还差多少"显示错） |

> **⚠️ 这不是本设计的问题，是既有代码的 P0。** 修它只要改 2 行数组，但它**卡住的东西比我这次做的所有设计加起来都大**。建议**优先于本设计的一切实现任务**处理。

## 一、好感度细化

### 1.1 六档够不够？——结论：**羁绊不再加档，恋爱另开一轨**

我把「六档扩到八档」这个直觉方案算了一遍账，**否掉了**。理由三条：

1. **档位名已经很好，扩档反而变差**。照面/眼熟/相熟/通意/同心/沁透 是一条完整的古风递进链，加 2 档只能插「同室/相知」这类**语义重叠**的名字（相熟↔同室、心同↔相知），玩家分不清。
2. **用户真正的缺口不是"档数少"，是"每档没有内容"**。现在 6 档只有数值和一句 `needNext` 文案，爬到「沁透」也**读不到任何新东西**。→ 该做的是**给每档配内容**，不是加档。
3. **恋爱不能靠"再加几档羁绊"实现**。若恋爱是 bond 的顶端，玩家会为了恋爱去刷 bond，于是**所有人都被推成恋爱向**——而想要家人感的玩家就被挤掉了。→ 必须**独立成轨、玩家显式开启**。

**所以：羁绊 6 档 → 扩到 8 档（补内容不补数量焦虑），另加一条「心意」4 轨。**

### 1.2 羁绊八档（`BOND_LEVELS` 扩到 8）

|---|---|---|---|---|---|

| 2 | **眼熟** | 12 | +12 | 记得你的习惯 | 陌生人 → 熟人 |
| 3 | **相熟** | 30 | +18 | 不用说话也知道你要做什么 | 家人雏形 |

**旧档兼容**：值是绝对值，只改阈值不改结构 → **老用户不会掉档**（只会提前到达同档）。零迁移。

### 1.3 心意轨（**新，恋爱向**）——4 档

羁绊是"我们有多亲"，心意是"**它是不是你的那个人**"。两条独立，互不换算。

| 档 | 名称 | 阈值 | 解锁 |
|---|---|---|---|
| 0 | 无 | 0 | 未启线（家人向玩法照常） |
| 1 | **微澜** | 40 | 它开始记得你今天会来 |
| 2 | **动心** | 100 | 双向确认，**恋爱线正式开启** |
| 3 | **倾心** | 190 | 独占的亲密剧情 |
| 4 | **相许** | 300 | 「新的日常形态」——**不另开恋爱终章**（见下） |

> **✅ 「相许之后」已定案（r3，采纳文案策划的论证）**：
> **恋爱线不设独立终章，相许的最终结算并进主线终局（岁除）。** 四条理由（我认同）：
> ① **相许 = 300 是数值满**，往上要么再加数值（立刻变刷分）、要么没有；
> ② **N 只各有终章会把后宫变成图鉴**——玩家为"收集终章"而玩，不是为角色；
> ③ **相许之后该是「新的日常形态」而非新剧情**：它不再需要盯着你了，会主动说"今天不用陪我，我自己练"——**因为它终于站住了**。这就是"长期与归处"的字面意思；
> ④ **唯一该有终章的是主线终局**（岁除榜挂出来）——**博爱在那天自然收束：谁跟你并肩站在榜下**。
>
> **⏳ 同时解锁的排序（已定：主线先）**：恋爱线锁化形、主线终卷也锁化形 → **两者同一时点解锁**，第 4 个月玩家会同时吃到两份大内容。
> **裁定：主线终局先放**（它带岁除倒计时，**有时限**）；**恋爱线次之**（**永久解锁，不急**）。

**⛔ 心意永不靠挂机涨**。只能由**玩家主动且需确认的举动**获得（§2.4 边界表）。这让"博爱"是有分量的行为，不是数值的自然溢出。

## 二、主动经营 vs 被动累积

### 2.1 配比数值（总表）

**被动降权，主动补上**——原被动太肥（陪伴+2/天、盘玩无上限），不降权则主动经营永远是装饰。

| 来源 | 原数值 | **新数值** | 上限 | 性质 |
|---|---|---|---|---|
| 陪伴（自然日，打开即结） | +2/天 | **+1/天** | 90 天回补（沿用） | 被动 |
| 盘玩 / 用心 | +1/次 | **+1/次** | **+2/日** | 被动 |
| 送礼 | — | **+4/件**（偏好命中 **+6**） | ≤2 件/日 | **主动** |
| 送礼·心绪日加成 | — | **×1.5**（封顶 +9） | 节令/生日当天 | 主动 |
| 照料（3 种） | — | **+2/次** | 3 种各 1 次/日（≤+6） | **主动** |

**照料三式**（非盘玩向的动作，三类串都有）：**擦净** / **静坐** / **理线**。

**「用心」统一定义（降级关键）**：
```
devoteOf(item, rec) = max(item.playCount, rec.devote)
```
- `rec.devote` 累计**盘玩 ∪ 照料**次数；
- 阶段门槛的"次数"读 `devoteOf`。
→ **库克/龙脊/紫金鼠**只做照料也能升阶；**菩提根**照常盘玩。**这就是优雅降级**（用户库房里只有菩提根会盘玩，其余三类靠这条活）。

### 2.3 ⛔ 轻度玩家不会被卡死（专项结论）

- **模型 7（零操作）**：拿得到 照面/眼熟/相熟 三档（day 30）。**这是有意的**——零输入用户不该拿到全部内容，但**必须拿到 3 档**，不能"永远到不了亲密阶段"。我把「相熟」的阶段门槛设为**无门槛**，就是为了兜住这一类。
- **模型 6（只做照料）**：**day 120 拿满沁透**。证明"不盘玩"不等于"到不了"——照料三重（擦净/静坐/理线）足以撑起全档。
- **沁透全档都在 day 120**：被**化形的 120 天硬门槛**压平。这不是坏事——它让**情感内容和修行进度天然同步**，不会有人先刷满情感再等着修行。反过来，任何玩家（含轻度）都**不会**因为送得多而在第 30 天就看完所有亲密内容。

| 规则 | 判定 | 理由 |
|---|---|---|
| 连续送礼递减 | 同一天第 2 件 **×0.5**（+4→+2） | 抑制"一天送爆" |
| 同一礼物重复送同一只 | ⛔ **无效**（`rec.giftLog` 已记 → 不消耗库存、不加羁绊、给一句"它已经收着呢"） | 防止把一件东西刷成万能 |
| 同一礼物送不同只 | ✅ **每只各一次** | **这是"博爱"的载体**——一盒点心分给三个人 |
| 同一只当日送礼 | **≤1 件**（全局 ≤2 件/日） | 焦点感 |
| 送礼资格 | 羁绊 ≥ **相熟**（它得先懂） | 前两档送了也是无反馈 |
| 恋爱向台词资格 | 心意 ≥ **动心** 且 stage ≥ **4** | 不越线 |
| 羁绊硬顶 | 99999（沿用 `addBond`） | |
| 心意硬顶 | 300（满即「相许」） | |

## 三、送礼系统

### 3.1 礼物从哪来（⛔ 不凭空发放，8 条自洽来源，**O(n) 单遍**）

| # | 来源 | 产出 | 节奏 | 依托现有代码 |
|---|---|---|---|---|
| 1 | **节令** | 1 件「应节物」 | 12/年（约 1 件/2.5 周） | `festOf` / `nextFest` ✅已有 |
| 2 | **修行破阶** | 1 件「开光物」 | 终身 4 件 | `stageOf` **检测到 stage 提升**时发（对比上次的 stage）✅ |
| 3 | **沁灵巷小事** | 命中特定 `TOWN_EVENTS` 主题给 1 件 | 约 1 件/2 天 | `TOWN_EVENTS` ✅已有，命中即可 |
| 4 | **同屋契合度** | 每跨一个 `STORY_STEPS` 档给 1 件 | 终身 5 件 | `STORY_STEPS=[7,20,40,70,110]` ✅已有 |
| 5 | **夜话事件** | 24 条里挑 8 条带奖励 | 约 1 件/1.5 周 | `NIGHT_EVENTS` ✅已有 |
| 6 | **主线章末** | 12 章里 8 章各给 1 件 | 前 80 天 | 主线脚本 ✅已有 |
| 7 | **成就** | 首次破阶 / 同一只收满 3 件 / 集齐五类偏好 | 稀疏 | 需新建（见 §7） |
| 8 | **每日一签** | 偶发"今日宜赠" | 约 1 件/周 | `SIGNS` ✅已有 |

> **⛔ O(n) 纪律**：所有产出都是**「按日期 × 单只」**计算，**没有一处是串两两枚举**。唯一的"全屋同发"（成就 #7「集齐五类」→给屋里每只 1 件）用**一次 `forEach`** O(n) 完成，不是 O(n²)。

**库存形态**：礼物是玩家级的（不是每只一份），但**送出后按只记账**。

### 3.2 偏好机制：**5 组人格 × 6 类礼物**

差异化的真实地基只有 **15 型人格 × 修行阶段 × 族类 × 玩家亲笔设定**，所以偏好只挂在**人格**上（阶段与族类只改措辞、不改命中）。

| 人格组 | 15 型归并 | 偏好类 | 典型礼物 |
|---|---|---|---|
| **软** | gentle 温柔安静 · sweet 娇憨可爱 · sentimental 多愁善感 · scholar 温润书卷 | **织物类** | 旧帕、暖石、护身香囊 |
| **动** | lively 活泼元气 · cheeky 古灵精怪 · heroic 侠气凛然 · wanderer 洒脱江湖 | **声响类** | 铜铃、彩绳、小拨鼓 |
| **素** | cool 高冷傲娇 · aloof 清冷疏离 · dignified 端方持重 · calm 沉稳可靠 | **器物类** | 白瓷茶则、素砚、旧香 |
| **奇** | mystery 神秘慵懒 · pampered 慵懒富贵 | **奇异类** | 琉璃小件、贝壳、会响的怪石 |
| **野** | wild 野性未驯 | **坚韧类** | 皮绳、磨刀石、粗布护腕 |
| *（通用）* | 全部 15 型 | **人情类** | 一碟点心、一盏热茶（不偏不倚，+4） |

**命中规则**：`命中偏好 = +6`，未命中 `+4`（1.5×）。**一族只有一类偏好，但 6 类都能送**——所以"送对"是划算，不是"送错就没用"。

**同族不同型的措辞差异**（这才是"每只都不一样"）：
- 族决定**它说什么**，型决定**它怎么说**。
- 例：同样「声响类·铜铃」，`lively` 是"它一听见就跟着晃"，`heroic` 是"它把铃攥在手里，像攥住什么兵器"。
- 修行阶段改**姿态**：`凝形`（4 头身）抱着铃像抱不下；`化形`（成人）把铃挂在腰上。

## 四、亲密剧情解锁

### 4.1 两类明确区分

| 类别 | 作用对象 | 尺度 | 数量 | 触发 |
|---|---|---|---|---|
| **阶段亲密剧情** | **单只专属** | 可深、可私 | 每档 2 段 × 8 档 = 16 段 | 羁绊档位 + 阶段门槛 |
| **群像羁绊事件** | **多只同场** | 家人般的相处 | 5 段（按 `STORY_STEPS`）+ 若干随机 | 同屋契合度跨档 |

**两类并行，不互斥**：一只串可以同时有自己的专属亲密剧情，又和同屋的伙伴一起经历群像事件。

### 4.2 羁绊档位 → 解锁内容对照表

| 档 | 阶段门槛 | 阶段亲密剧情（单只专属） | 群像羁绊事件 | 心意轨 |
|---|---|---|---|---|
| 1 照面 | 无 | 「它记住你手边的位置」 | — | — |
| 2 眼熟 | 无 | 「它替你留了一盏灯」 | — | — |
| 3 相熟 | 无 | 「不用说话也知道你要什么」 | — | — |
| 4 同室 | 开窍(7天+5) | 「你回来晚了，它没问」 | 契合度 7：**同屋第一夜** | — |
| 5 通意 | 开窍 | 「它知道你不说的那半句」 | 契合度 20：**谁帮谁挡了一次** | — |
| 6 同心 | 蜕形(30天+20) | 「你不在时，它有事做」 | 契合度 40：**一件外套轮流穿** | 微澜(40) |
| 7 相知 | 蜕形 | 「它能替你拿一个主意」 | 契合度 70：**替对方圆一个谎** | 动心(100) → **恋爱线开启** |
| 8 沁透 | 化形(120天+60) | 「不必解释」 | 契合度 110：**院子里的长夜** | 倾心(190) → 相许(300) |

**⛔ 恋爱线的三重锁**（任一不满足即不可见）：
```
恋爱线开启 = 羁绊 ≥ 相知(200)  AND  stage ≥ 4(化形)  AND  玩家在「心迹」页显式点「我想和它更近一步」
```

### 4.3 ⛔ 尺度硬红线（**最重要的一条在最后**）

| | 允许 | 禁止 |
|---|---|---|
| **关系性质** | 明确的心动、双向奔赴、「不只是同伴」 | — |
| **表达** | 牵手、等候、记住你的习惯、替你挡事 | 占有/控制/囚禁、「你只能属于我」 |
| **同伴间** | 多只同场、互相照顾、家人般的松弛 | 贬低他人、争风吃醋、把同伴当敌人 |
| **身体尺度** | 牵手、拥抱、额头抵着、衣料与体温的描写 | 露骨性描写、衣不蔽体 |
| **🔴 形态红线（硬约束）** | 恋爱向内容**仅限 stage ≥ 4（化形，成人形态）** | ⛔ **任何恋爱向台词不得在 `stage < 4` 出现** |

**🔴 这条为什么是硬红线（不是风格偏好）**：代码里 `STAGES` 明写 `凝形=4头身婴儿`、`开窍=6头身小孩`、`蜕形=8头身少年`。**在未成形的形态上写恋爱，既是伦理问题也是合规风险。** 所以：
- `心意轨` 萌芽（微澜）可在 **stage ≥ 3** 开始积累，但文案**严格停在"在意/惦记/等你来"**，**绝不表白**；
- 唯一定性关系的动作「表明心意」**必须 stage ≥ 4**；
- 全部恋爱向剧情的门槛 = **stage ≥ 4**；
- 家人向内容**不受此限**（8 档全阶段可读）。

**世界观支撑**：设定明确「化形之后它们**是生命、是仙**」。所以恋爱线的**物理前提就是"它成年了"**——这不是束缚，**它给了恋爱线一个天然的、庄重的解锁仪式**：你必须陪它走完 120 天，它才以成人的样子站在你面前。

### 4.4 「每只都不一样」怎么做到（用户核心诉求）

三重差异化叠乘，**不需要两两枚举**（单只判定 O(1)）：

```
内容键 = 羁绊档位 × 15 人格 × 修行阶段 × 玩家亲笔设定(look.persona)
```

| 层 | 变的是什么 | 例子 |
|---|---|---|
| **羁绊档位** | 关系的**深度** | 同心档 = "你不在时它有事做"；相知档 = "它能替你拿主意" |
| **15 人格** | 关系的**说法** | `calm` 沉稳可靠 → 它默默做完；`aloof` 清冷疏离 → 它嘴上说"没有"却已做好 |
| **修行阶段** | 关系的**姿态** | 凝形（4头身）仰头看你；化形（成人）平视你 |
| **玩家亲笔设定** | 关系的**专名** | 玩家写的 `look.persona`（名字、来历、你们之间的旧事）直接进台词 |

**降维提示**：`15 人格 × 4 阶段 × 8 档 = 480` 组合**不需要 480 段文案**——按**人格组（5）× 档位（8）= 40 段骨架**写，阶段与亲笔设定做**槽位替换**。这是可实现的。

### 4.5 对比样例（可直接读给用户）

**【样例 1】同一档位「同心」，两只不同人格——完全是两段东西**

**A · 沉稳可靠（calm）**
> 那天收摊得早。你进门时，灯已经点上了，热的那一盏。
> 「回来了。」
> 「嗯。」
> 它没问你去了哪儿，只把桌上那碗粥往你这边推。碗底还温着——它算过你回来的时辰。
> 你坐下，它才去洗手。洗完也不走，就靠在门边看你吃。
> 「……你今天笑了一下。」
> 「没有。」
> 「有。」

**B · 清冷疏离（aloof）**
> 你回来的时候，屋里是暗的。
> 「……灯呢？」
> 「忘了。」
> 你去点，它拦了一下，没拦住。灯亮起来，你看见它坐在窗台上，膝盖摊着一本很久没翻的书，一个字也没看。
> 「等我？」
> 「没有等。」它把书合上，「只是这个姿势比较省力。」
> 你笑出声。它别过脸，但没有从窗台上下来。

> **差异点**：A 的深情是**做出来的**（留灯、推粥、算时辰），全程不表白；B 的深情是**藏出来的**（嘴硬、找借口、别过脸）。同一档位、同一件事（你晚归），两种完全不同的爱法。

**【样例 2】同一只沁灵（温润书卷 scholar），家人线 vs 恋爱线**

**家人线（同心档，stage 3）**
> 你在书房坐了一下午，起身要走。
> 「等等。」
> 它从架上抽了一册，夹了张纸条，递给你：「看到第三页。」
> 你打开。第三页有它的小字：「这里我不懂，留给你。」
> 「……你留给我不懂的？」
> 「不懂才要给你。」它把灯往你那边挪了挪，「懂的东西它自己会了。」
> 你走的时候，它已经在把窗合上了——留了一指宽的缝，风进不来，透气就行。

**恋爱线（相知档，stage 4 化形 + 你已确认「更近一步」）**
> 你又来了。
> 它这次没等在窗边，站在门口，像是走了很久。
> 「你每次来，都说是顺路。」
> 「……是顺路。」
> 「这条路不通你家。」
> 你笑了。它没生气，只是垂下眼睛，很小声地说了句：
> 「我不是要你承认什么。我只是……想听你说一次，你专门来的。」
> 「我专门来的。」
> 它抬起头看了你很久，耳朵尖有点红。
> 「……嗯。我知道。」

> **差异点**：家人线里它给你的是**知识与位置**（留一册不懂的书、留一指宽的窗缝）——"我在帮你成为你"；恋爱线里它要的是**一句实话**（"你专门来的"）——"我需要你承认我在你心里有位置"。**同一只、同一档位区间，因为关系性质不同，给出的东西完全不同。**

## 五、多线并行 / 博爱（用户最兴奋的点）

### 5.1 核心结论

**不做总量上限。** 羁绊和心意都是 **per-string** 存档，天然独立、互不影响——玩家可以同时对 8 只走恋爱线，这就是「开后宫」。

### 5.2 防"退化成纯数值堆砌"的五个机制

| # | 机制 | 做法 |
|---|---|---|
| 1 | **信物收藏** | 每条恋爱线成立时给**一件专属信物**（`rec.trinket`），**全不重样、可同时持有**。博爱不是数字，是**一堆独一无二的信物**——可回看、可截图、可带出 |
| 2 | **心上人（唯一）** | 可标记 **1 只**为「心上人」，享专属称呼与终章。其余为「知己」。**恋爱线数量不限，只多一个"最珍视"** |
| 3 | **不同线不相冲** | 世界观是同伴/家人 → 同伴之间**不争风吃醋**。多只同场走的是**群像羁绊**（家人般的松弛），不是修罗场。**这既合规、又让用户舒服** |
| 4 | **差异化保证** | 靠 §4.4 的三重叠乘：**即使同时推进 5 条，因为人格不同，内容天然不同**，不存在"复制粘贴的第五份" |
| 5 | **不衰减、不清零** | 30 天不互动 → **冻结而非掉分**。只"相许"档需 30 天内互动才续期。**惩罚只针对"挂机式后宫"，且从不estructive** |

### 5.3 「共情会不会互相稀释？」——我的回答

**会，如果内容是可复制的模板；不会，如果每条线有自己的记忆。** 所以设计上：

- 每条线**独立存档**：`rec.heart` / `rec.heartLog` / `rec.trinket` **全在各自的 rec 里**（不存全局）；
- 玩家在不同线上的**选择互不可见**（A 线的选项不影响 B 线），**避免"我为了 B 让 A 难过"的负罪感**；
- 但**群像事件里它们同场**——这时才有"多个你"在同一屋檐下的**轻微张力**（不是冲突，是热闹）。这是**加分而非稀释**。

### 6.1 三条来自实战的尺度标尺（r3 · 写档 4/7/8 前必读）

| 档 | 陷阱 | 正确写法 | 出处 |
|---|---|---|---|
| **4 同室** | 🔴 **7 天写不出依恋。** 若写成"它很想你"，7 天的设定立刻假 | **必须写一件具体的小事，不能写一种感情。** 标杆：「你回来晚了，它没问。」——它好**恰恰因为是一件小事** | v4 §3.1.2 |
| **7 相知** | 🔴 存在一个状态：**「它已经准备好了，但你没开口」**（羁绊刷满但没点那个按钮）。⛔ 不能变成责怪（"你都走到这一步了怎么还不点"）⛔ 不能暗示不点就来不及 | **把"没开口"写成它的一种等待，不是一种期待。** 它不催、也不设期限——**门一直开着** | v4 §3.1.2 |

### 7.3 🔴 占位符空值兜底规则（已知落差）

`fmt`（`:2043`）空值会**原样输出 `{xxx}` 给玩家**。`thText`（`:3836`）**只吃 ASCII key**。

**规定**：
1. **送礼/亲密剧情的文案一律不走 `fmt`**，改走新函数 `safeFill`：
   ```js
   // 兜底值必须可读，不允许空串；未命中时用兜底句，绝不吐 {xxx}
   function safeFill(tpl, vars, fb = {}) {
     return String(tpl).replace(/\{(\w+)\}/g, (m, k) => {
       const v = vars[k];
       return (v == null || v === "") ? (fb[k] != null ? String(fb[k]) : "") : String(v);
     });
   }
   ```
2. **中文占位符禁令**：`thText` 路径**只用 ASCII key**（`{gname}`/`{you}`），**中文 `{胎性}` 只能在 `fmt` 路径**（这条同时规避了 `thText` 未修的坑）。
3. **每个新占位符必须登记兜底值**：

| 占位符 | 兜底值 | 说明 |
|---|---|---|
| `{礼物}` | 「那样东西」 | |
| `{它}` | 「它」 | |
| `{信物}` | 「那件信物」 | |
| `{你}` | 「你」 | |
| `{称呼}` | 「主人」 | 对齐 `callOf` |

## 八、🔴 恋爱门控的落地写法（已定案：代码门控）

### 8.1 断言放哪（三处，缺一不可）

⛔ **不能只写在文案条件里**。文案条件是"剧本自觉"，架构师新增恋爱内容时可能忘写。**必须在引擎入口做物理拦截。**

| # | 位置 | 写法 | 拦什么 |
|---|---|---|---|
| **A** | `intimateAct(rec, actId)` —— **新增的统一入口**，所有恋爱向动作走它 | `if (stageOf(item, rec, now) < 4) return { ok:false, why:"locked" }` | ⛔ 一切恋爱向动作（表明心意/赠贴身物/共度/化解别扭/回应试探） |
| **B** | `heartLineOn(rec)` | 同上，且**额外**要求 `bondOf(rec) >= 200` | ⛔ 恋爱线开关本身 |
| **C** | 恋爱剧情读取处（`intimateSceneOf`） | 读取前再判一次 `stage >= 4`，**不信任调用方已判过** | ⛔ 旧存档 / 降级 / 异常路径 |

> **为什么三处都要**：A 是入口（防新代码漏判）、B 是开关（防未确认就进线）、C 是读取（防绕过入口直接读存档）。**读取处那道是最后一道闸**——历史上最贵的 bug 都是"存档里有、但条件不满足"。

### 8.2 怎么测（不靠肉眼）

| # | 测试 | 期望 |
|---|---|---|
| T1 | 造 `stage=3`（蜕形）的 rec，调 `intimateAct(rec,"confess")` | 返回 `ok:false, why:"locked"`，**且 `rec.heart` 不变** |
| T2 | 造 `stage=3` + 直接写 `rec.heart=300`（伪造存档），调 `intimateSceneOf` | **返回 null**，不吐任何恋爱文案 |
| T3 | 造 `stage=4` + `bond=200` + 未确认，调 `heartLineOn` | `ok:false, why:"not-confirmed"` |
| T4 | 造 `stage=4` + `bond=200` + 已确认 | `ok:true`，`rec.heart += 60` |
| T5 | **全量扫描**：遍历恋爱文案表，断言每条都带 `stage:4` 元数据 | 缺元数据的条目 → **测试失败**（防新增文案漏标） |
| T6 | 把某条恋爱文案的 `stage` 从 4 改成 3 | T5 仍通过（因为有 stage 门），但 **T2 必须仍返回 null** |

> **T5 是最重要的一条**：它把"新写恋爱文案必须声明 stage"变成**编译期/测试期可见**，而不是上线后靠人肉 review。

### 8.3 世界观理由（用你认可的那条）
设定已明确「**化形之后它们是生命、是仙**」。所以恋爱线的**物理前提就是它成年了**——这道门不是束缚，是**让 120 天的陪伴有一个庄重的兑现时刻**。文案上建议在首次解锁时点明这层：「它站在你面前的样子，和一百二十天前不一样了。」

### 9.2 ⛔ `~global` 方案为什么否决（这是本次审计最重要的产出）

`ww_spirits` 的 value 被**全项目 4 处「整库遍历」**假设为 rec。塞一个非 rec 的 key 进去，逐处审计结果：

| # | 位置 | 代码 | 对 `~global` 会发生什么 | 后果 |
|---|---|---|---|---|
| **1** | `spirits.js:312` `pruneForQuota` | `Object.keys(o).forEach(k => { const r=o[k]; if(!r\|\|typeof r!=="object") return; ...})` | 守卫**放行**（它是 object）→ 对它执行整套裁剪，并调 `dropOldCgThumbs` | 🟡 往 `~global` 里塞 `r.marks`/`r.fests` 等**垃圾字段**，体积虚增 |

| **3** | `app.js:6347` 重画清图 | `Object.keys(st).forEach(k => { st[k].imgUrl=""; st[k].imgAt=0; ... })` | 往 `~global` 写 6 个 `img*` 字段 | 🟡 污染 |

## 十、🔴 「帮它修行」机制（新增联动）

### 10.1 形态红线先行

⛔ **「帮」绝不能是物化动作**——不盘、不塞柜、不挂、不擦。必须是**修行路上的同行**：安排机会、在关口替它做决定、给它指一条路、替它挡一道关。

### 10.2 机制：「关口 · 同行」= **纯见证，不改任何晋阶速度**

> **🔴 r3 重大修订（采纳文案策划 v4 §3.1.3 的硬约束，我撤回原方案）**
> 原方案让「替它挡关」`devoteOf += 8`、「指一条路」天数 −15 天 —— **两条都撤回**。
> 理由（文案策划的论证成立，我认同）：**4 阶门槛是唯一保证"帮再多也不能跳级"的机制**；一旦帮修行能加速，
> 「你没帮它」就等于「它慢了」，而**"来不及"是系统制造的**——那不是选择，是 **guilt**，与用户最高原则「**系统不主动杀**」直接冲突。
> **本节现在的立场：帮修行对 `stageOf(days, plays)` 的影响恒等于 0。** 判定函数只认"过了多少天"和"上手多少次"。

| 动作 | 条件 | 效果 | 代价 |
|---|---|---|---|
| **在关口陪它 / 替它做决定** | 羁绊 ≥ **同心(140)** + 窗口未过 | 羁绊 **+12** + 专属事件卡 + 该关口独特产物 | 占用当日 **1 次**全局「同行」机会 |
| **给它指一条路** | 羁绊 ≥ **相知(200)** | 羁绊 **+12** + 事件卡；⛔ **不改任何门槛** | 同上 |
| **H2 型：它拒绝被安排**（`aloof`/`wild`/`dignified`） | — | ⛔ **它有权拒绝你**——只能改"指路"，不能替它决定 | — |

**⛔ 代价（只允许机会成本，且不含任何"来不及"）**：
- **机会成本**：帮它 = 占用今天唯一的「同行」机会 → **帮了 A，B 的窗口就可能过期**。
- **窗口过期不惩罚**：关口**自己过了**，不扣分、不锁定。**它绝不会因为你没帮而落后。**
- **不设死亡 / 失败 / 损毁 / 落后。**

### 10.3 ⭐ 数值交织的地基：**帮修行不碰 `stageOf`（影响恒为 0）**

> 阶段门槛是**双条件 AND**（`STAGE_DAYS` ∧ `STAGE_PLAYS`，`spirits.js:732-735`），
> 修好 P0 后为 **7天+5次 / 30天+20次 / 120天+60次**。
> **帮修行只产出「羁绊 + 事件 + 产物」，一个门槛数字都不碰。**

| 阶段 | 天数门槛 | 次数门槛 | 帮修行的影响 |
|---|---|---|---|
| 开窍 | 7 | 5 | **0** |
| 蜕形 | 30 | 20 | **0** |
| 化形 | 120 | 60 | **0** |

### 10.4 ♻️ 节奏测算：**因帮修行不影响门槛，节奏表与 v1 完全一致，无需重算**

这是"不碰 `stageOf`"最干净的结果——**没有任何一个解锁日会因帮修行而移动**。

| 模型 | 动作/日 | 帮修行 | 开窍 | 蜕形 | 化形 | 与 §2.2 对比 |
|---|---|---|---|---|---|---|
| 1 重度全勤 | 6 | 常帮 | 7 | 30 | **120** | **完全一致** |
| 3 中度均衡 | 3 | 偶帮 | 7 | 30 | **120** | **完全一致** |
| 5 轻度混合 | 1.29 | 偶帮 | 7 | 30 | **120** | **完全一致** |
| 6 轻度只读 | 1.29 | 偶帮 | 7 | 30 | **120** | **完全一致** |
| 7 极轻零操作 | 0 | 不能帮（羁绊不够） | — | — | — | 不适用 |

**→ §2.2 的九模型节奏表原样成立。** 且现在它**更强**了：因为不存在任何"帮了能更快"的通道，**情感内容在结构上不可能超前于修行进度**。

### 10.5 ⚠️ `devoteOf` 的定位降级（诚实修正）

原方案用 `devoteOf = max(playCount, rec.devote)` 让**照料**（擦净/静坐/理线）计入晋阶次数。我曾把它当"降级关键"，**现在降级为「待裁决的等价通道」**：

- **事实核对**：`playCount` 的两处自增（`app.js:1354` 手动补记盘玩日期、`:1574` 「今日已盘」按钮）**都不判品种**，所以库克/龙脊/紫金鼠 **并非被锁死**——它们同样能靠这两个入口累计次数。
- **所以 `devoteOf` 不是 P0，是 nice-to-have。** 它只解决"愿意照料、但不愿按「今日已盘」"的那部分玩家。
- **它仍然构成"给 `stageOf` 新增第三个输入"**（`rec.devote`），与文案策划「只认两个东西」的约束**同样冲突** → **交主理人裁决，我不坚持**。

> **我的建议**：若要采纳，请把它明确表述为「**照料 ≡ 盘玩**（等价通道，1 次照料 = 1 次盘玩）」，而**不是**「额外加速」——前者不产生 guilt（你没有落后），后者才会。

### 10.6 与送礼的关系：**不互相替代**（主理人关心的第 4 点）

| 维度 | 送礼 | 帮修行 |
|---|---|---|
| 频次 | **可刷**（每日 2 件） | **不可刷**（全阶仅 4 次关口，终身上限） |
| 羁绊贡献 | +4~6 / 件，**30 天可 +360** | **+12 / 次，全阶累计仅 +48** |
| 性质 | **关系向**（日常照顾） | **事业向**（修行路上的同行） |
| 错过的代价 | 无 | **关口窗口过期 = 永久失去这次助力** |
| 给心意 | 可（化形后，赠贴身物 +35） | ⛔ **绝不给** |

**三条防替代设计**：
1. **总量差一个数量级**：帮修行全阶最多 +48 羁绊，送礼 30 天可 +360 → **帮修行不可能取代送礼**。
2. **帮修行不可刷**：窗口有限、终身 4 次 → 它是**叙事事件**不是**数值来源**。
3. **⛔ 帮修行绝不给心意**：恋爱向只能通过"明确主动的亲密举动"获得，**事业线帮忙不能顺带刷出爱情**——否则恋爱线的分量会被稀释。

### 10.7 「帮修行」的叙事分量（保住它不当成刷数值）

- 每次帮修行**必出一张事件卡**（走 `recordEvent`，`spirits.js:753`），内容是**它的反应**而非数值播报。
- ⛔ **事件卡里不出现 "+8 次数""省了 8 次盘玩"** 这类字样。只写它说了什么、做了什么。
- 帮修行**不计入每日照料/送礼的次数上限**（独立预算），但**共享「同行」这 1 次/天的全局机会**——所以它必然与陪伴其他串争夺时间，**这才是它真正的代价**。

## 十二、自评（team-lead 要的第 ⑦ 项）

### 12.1 这套设计能否撑起"家庭式依恋与照顾"？

**能，而且我认为这版的骨架比上一版更对。** 三个理由：

1. **家人感不靠"克制"获得，靠"日常细节"获得**。§4.5 样例 1 里，`calm` 的深情是「留灯、推粥、算时辰」——**没有一句表白，但比表白重**。这证明家人感可以完全由**动作**承载，不依赖尺度的收放。
2. **把「主动经营」接在了羁绊上而不是恋爱上**。玩家通过擦净/静坐/理线/递东西把一段关系养热，这个过程本身**就是家人的质感**；恋爱线只是这份积累走到某处后**可选的另一个方向**。
3. **`devoteOf`**（我曾称"降级关键"，**r3 已降级为待裁决项**）：核代码后确认 `playCount` 两处自增都不判品种，**没有串被锁死**，所以它不是 P0。它只服务"愿意照料、但不愿按「今日盘过」"的那部分玩家。⛔ 建议若采纳，表述为「**照料 ≡ 盘玩**（等价）」而非「额外加速」——见 §10.5。

### 12.2 最容易被做成「恋爱向」而需要你盯住的地方

按风险从高到低：

| 风险 | 在哪 | 怎么盯 |
|---|---|---|
| **🔴 形态** | 化形前（凝形 4 头身婴儿 / 开窍 6 头身小孩 / 蜕形 8 头身少年）写出恋爱感 | ✅ **已定案为代码门控**：`intimateAct` 入口断言 + `heartLineOn` 开关断言 + **读取处再判一次**（§8.1 三处）；测试 T1-T6，其中 **T5 强制恋爱文案带 `stage:4` 元数据** |
| **占有/控制语** | 文案最容易滑进去的地方（"你只能陪我""不许去那边"） | §6 对照表 #8 已给正例（**在意但不索取**）。建议把所有含「你只能」「不许」「永远属于」类的句子列为**禁用词**，写进文案 checklist |
| **同伴吃醋** | 多线并行时，文案很容易写成"两只为你争风吃醋" | §5.2 机制 3 已定调：**同伴不争抢**，冲突改为群像的热闹。盯住任何"它看见你送别人后…"的句式 |
| **恋爱向内容超前于修行** | 玩家送得多、玩得多，可能在第 30 天就把恋爱内容看光 | 已用**化形 120 天**硬压平（§2.3）；**r3 后更强**——帮修行对 `stageOf` 影响 **= 0**（§10.3），**结构上不存在任何"帮了更快"的通道**。盯住的是**别为了"让玩家早点看到"而放松化形那道门** |
| **恋爱线吞掉家人线** | 玩家全开后宫，每只都走恋爱向，家庭感被稀释 | 建议保留**至少 1-2 条纯家人线**（不确认「更近一步」即为家人线），并在设定文案里点明"**不确认也是可以的**" |

### 12.3 「帮它修行」会不会被做成刷数值？我自评（r3 已自我修正）

**⚠️ 先认错**：我原方案（挡关 +8 次数 / 指路 −15 天）**已撤回**。真正的风险不是数值，是——**它把一个"选择"变成了"责任"**：帮了能更快，那么「你没帮它」就等于「它慢了」，而**"来不及"是系统制造的**。这与用户最高原则「**系统不主动杀**」直接冲突。**文案的论证成立，我认同。**

**现在的三道防线**：

| 防线 | 做法 | 为什么够 |
|---|---|---|
| **⛔ 不碰门槛** | 帮修行对 `stageOf` 影响 **= 0** | **结构上**杜绝"帮了更快"，也就杜绝了 guilt |
| **不可刷** | 终身 4 个关口、每关有窗口、过期作废 | 羁绊累计上限 **+48**，不到送礼 30 天收益（+360）的 1/7 |
| **不给心意 + 卡面无数字** | ⛔ 不加 `rec.heart`；事件卡只写反应 | 保住"恋爱只能靠明确主动的亲密举动"这条唯一性 |

**✅ 采纳文案 v4 §3.2 的 H1–H5，我不再另写关口文案。** 他们已内置我担心的两条防线：
- ⛔ **不做数字播报**（v4 §3.3.1）；
- ⭐ **H2 专门解决"分歧"**：`aloof` 不接受被安排 / `wild` 自己冲 / `dignified` 要先问——**这三型你只能指路，它有权拒绝你**。v4 §3.5 把它列为「帮不动的三种设计」之首：**它保证「帮」不等于「控制」**。这比我提的"让两者产生分歧"更彻底，**我撤回上轮请他们新写 4 个关口的请求**。
