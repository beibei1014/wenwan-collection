## 0. 为什么要这份规范（问题溯源）

用户实测三条痛点，逐条对应根因：

| 用户原话 | 现象 | 根因（已查代码确认） |
|---|---|---|
| "出的立绘和设定有出入" | 模型自作主张 | `appearancePrompt`(spirits.js:614) 只锚定 gender/eyes/acc/outfit/pattern/material，**用户写的动作/持物/颜色没进 prompt**，模型按随机池自由发挥 |
| "写了'捧着绣球花'却出了'拿竹简'" | 持物被替换 | 持物来自 `appearanceOf` 随机抽的 `PROPS`(ap.prop)，用户原文里的"绣球花"既没被抽出、也没被强制写入 |
| "动作相对固定 / 衣服颜色也很固定" | 千篇一律 | 随机池每次抽同几类；颜色走 `OUTFITS` 池色，不读用户写在人设里的颜色词 |
| "三只手四只手" | 解剖翻车 | `ANATOMY` 常量虽在，但姿态指令一旦复杂（遮叠手臂、双手各持物），模型仍易多画肢体 |

**一句话定位**：现有管线"先出图、再看、再改"，等于每次不满意都白烧 1 次额度。本规范改成"**先按人设提炼成草稿 → 展示给用户确认 → 确认后才出图**"，既保住人设还原，又把出图钱花在刀刃上。

## 1. 三条铁律与裁决优先级

本规范优先级低于「不破坏数据/不破坏状态机」等全局红线（见 `v163-架构师下单件.md` §1），但在**出图内容层面**以此为裁决顺序：

1. **古风统一**：`GUOFENG` / `NEG_STYLE` 不可破（禁日式符号、禁西式现代服装、禁夸张表情）。用户写了违规内容（如"穿西装"），以古风为准改写并提示。
2. **省出图钱**：**未确认绝不出图**。任何"先出一张看看"的念头一律否决——确认环节本身就是省钱环节。
3. **防解剖错误**：`ANATOMY` 强制写入；自检不过，禁止出图，退回重提。

**冲突裁决表**（人设 vs 其它）：

| 冲突场景 | 裁决 | 动作 |
|---|---|---|
| 用户写的动作/持物/颜色 vs 随机锚定项 | **用户写 > 随机抽** | 用户原文强制覆盖随机值 |
| 用户写的设定 vs 古风约束 | **古风优先** | 改写违规表述，卡片里给出"已按古风调整"提示 |
| 用户写的设定 vs 解剖安全（如"三头六臂""双手各举三件"） | **解剖优先** | 降级为"双手简单清楚"的安全姿态，提示用户 |
| 用户没写的项目（发型/姿态细节） | **自由发挥，不锁死** | 交给古风仪态池参考，AI 按人设判断 |

> 规则精神：用户**明确写过的**，必须原样呈现；用户**没写的**，才允许系统补。绝不允许系统替用户"优化"掉用户写的内容（这是绣球花变竹简的直接原因）。

## 2. 提炼 SOP（输入 → 输出）

### 2.1 输入清单

| 类别 | 字段（均来自现有 `rec`，零新存储） | 用途 |
|---|---|---|
| 用户人设·原文 | `rec.look.base`（用户给的设定原话） | 优先抽取 动作/持物/颜色 |
| 用户人设·融合 | `rec.look.profile`（已有融合设定，可能含 base 之外细节） | 补充抽取，与 base 一致不矛盾 |
| 用户人设·发色 | `rec.look.hairc` + `rec.look.customColor`（bead/custom/auto/pick） | 发色与色值 |
| 用户人设·特征 | `rec.look.feats`（猫耳/狐尾等，最多 3） | 特殊特征 |
| 用户人设·胎性 | `rec.look.pers`（cool/cheeky…） | 气质基调 |
| AI 补充人设 | `rec.personaZh`（200–300 字中文人物设定，spirits.js:1865） | 润色与兜底抽取（**不作覆盖用**） |
| AI 名片 | `rec.persona{name,title,traits,line}` | 称号/口头禅等文本 |
| 系统锚定项 | `appearanceOf` 抽到的 gender/eyes/acc/acc2/outfit/pattern/material | 固定锚定，**不可被随机覆盖** |

### 2.2 输出结构（"立绘/场景描述草稿"）

提炼器输出一个**结构化草稿** `LookBrief`，每一项都要能在确认卡上逐条展示：

```
LookBrief = {
  gender,                       // 性别（锚定）
  pose,        poseZh,          // 动作（来自用户原文优先；否则古风仪态池）
  prop,        propZh,          // 持物（来自用户原文；绝不替换）
  outfit,      outfitZh,        // 服饰款式（襦裙/长衫/褙子…）
  colors: [ {part, cn, hex} ],  // 颜色表：发/衣/里/饰… 传统色名 + 具体色值
  hairstyle,  hairstyleZh,      // 发型（用户写过则呈现；否则自由）
  feats,                        // 特征（来自 rec.look.feats）
  scene,       sceneZh,         // 场景（背景/光线，立绘可极简，CG 必填）
  styleBits,                    // 强制风格位（GUOFENG+NEG_STYLE+CONSISTENCY+SINGLE）
  anatomyBits,                  // 强制解剖位（ANATOMY + 姿态简化指令）
}
```

最终的出图 prompt = `styleBits + anatomyBits + 由 LookBrief 逐字段翻译的英文句 + 形态阶段描述(STAGES)`。**用户原文抽出的 动作/持物/颜色 必须逐字进入 prompt，不允许被随机池二次覆盖。**

### 2.3 提取规则（核心，逐条可执行）

**动作（pose）**
- 扫描 `rec.look.base` + `rec.look.profile` + `rec.personaZh` 中**显式**的仪态/动作描述（作揖、拱手、拂袖、团扇半遮面、低眸捻珠、执笔、捧盏、展卷、捧着X、抱某物…）。
- 命中 → 用该动作，**用户写过的优先于随机 `POSES` 池**。
- 未命中 → 不锁死，交古风仪态池 `POSES_ZH`(spirits.js:510) 参考，由 AI 按人设判断自然姿态。
- 约束：姿态必须"简单清楚、双手位置明确、不遮叠手臂"，复杂手势一律降级（见 §4）。

**持物（prop）**
- 扫描用户原文中**具体物件**（绣球花、竹简、团扇、盏、卷、珠串、灯笼…）。
- **命中即固定**：写成对应英文（`holding a bouquet of hydrangea flowers`），写进 prompt 的 prop 位，**绝不许替换成 `PROPS` 随机池里别的物件**。
- 用户没写持物 → 才允许回落 `appearanceOf` 的 `ap.prop` 或留空。
- 若用户同时写"双手各持一物"，触发 §4 自检第②条，降级为单手持物或简化。

**服饰颜色（outfit color）**
- 扫描 `rec.personaZh` / base 中衣物**颜色词**（黛色、月白、胭脂、天青、秋香…）。
- 命中 → 走 §2.4 颜色映射，得到「传统色名 + #hex」，**用户写的颜色覆盖 `OUTFITS` 池色**。
- 服饰**款式**（襦裙/长衫/褙子/道袍…）同样从人设取；系统只兜底未知款式。

**发型（hairstyle）**
- 用户写过 → 呈现（长直/发髻/发冠/马尾/辫/披发…）。
- 用户没写 → **不锁死**，自由发挥（立项已定：古风发型多样，不硬套短发）。
- 发**色**走 `rec.look.hairc/customColor`，映射见 §2.4。

### 2.4 颜色映射算法（中国传统色 ↔ 具体色值）

直接复用现有两套能力，**不要新造颜色表**：

1. 用户给 **#hex**（customColor 以 `#` 开头）：先 `hexToCnTrad(hex)`(spirits.js:977) 取最近传统色名，prompt 写成「`〈色名〉 (#hex)`」——既保色值 fidelity，又带古风字眼。
2. 用户给 **中国传统色名**（在 `CN_TRAD_COLORS`(spirits.js:928) 或 `COLOR_WORD_ZH`(spirits.js:990) 中）：反查 hex，写成「`〈色名〉 (#hex)`」。
3. 用户选 **bead（跟珠子）**：取 `beadColor(item)` 的 `zh` + `hex`。
4. 用户选 **auto**：沿用现有分散池（按 id+seed 稳定挑，避免每只同色）。
5. **兜底纪律**：任何未识别颜色，回落到 `CN_TRAD_COLORS` 里取最近色；**绝不允许输出霓虹/荧光/马卡龙等非传统色**——那是破古风。

> 输出到 prompt 时，颜色一律"名 + 值"双写（如 `hair color: 胭脂 (#9d2933)`），让模型既懂字也懂数值，避免色偏。

### 2.5 兜底与改写

- 古风冲突改写：用户写了"西装/运动服/T恤"等，`NEG_STYLE` 已禁，按 `v163-CG相册与美术规范.md` §B0 的改写逻辑改成"中式长衫/褙子"类，并在确认卡"风格"行标注"已按古风调整"。
- 解剖冲突改写：用户写"三头六臂""双手各举多件"，触发 §4 降级，卡片提示"已调整为双手简单清楚的姿态"。

## 3. 风格一致性守则

以下常量**逐字沿用，一行不动**（与 `v163-CG相册与美术规范.md` §B0 一致）：

- `GUOFENG`(spirits.js:541)：中式古风、汉服发型、丝绸锦缎、古典配色。
- `NEG_STYLE`(spirits.js:531)：禁日式符号 / 禁西式现代服装 / 禁 V 字手势与坏笑 wink / 禁解剖错误 / 温和中性表情。
- `CONSISTENCY`(spirits.js:630)：跨阶段同人同色同饰，只长大不变性。
- `SINGLE`(spirits.js:636)：只画一人、无分格、无文字。

三条落地纪律：

1. **古风统一**：正面风格位 + 负面约束位每图必带，不随用户偏好开关。
2. **动作/发型不锁死**：用户没写就自由发挥（古风仪态池参考），但**用户写过的必须呈现**（§2.3）。
3. **确认卡里"风格"和"一致性"作为只读行**：用户可改 动作/持物/颜色/场景，但改不了"古风"与"同人同色"——从源头堵住破风格。

## 4. 解剖学防错清单（写入立绘 prompt 的强制 bits）

### 4.1 强制位（每次出图都拼进去）

- `ANATOMY`(spirits.js:537) **逐字**：`strictly correct human anatomy, exactly two arms and two hands, five fingers per hand, simple clear hand shapes, both hands resting naturally and unobstructed, no extra limbs, no extra hands, no extra fingers, no hidden overlapping arms, no detached floating hand`。
- **姿态简化指令（新增、与 ANATOMY 同组）**：`simple clear posture, both arms and hands fully visible and uncrossed, no overlapping or hidden arms, avoid complex hand gestures that risk extra limbs or extra fingers`。——复杂手势是"三只手/多指"的头号诱因，从源头压住。

### 4.2 确认前自检（程序断言，不过则禁出图）

提炼器产出 `LookBrief` 后、展示确认卡**之前**，跑 4 项断言，任一失败 → 草稿标红、不允许出图、退回重提：

| # | 断言 | 失败处理 |
|---|---|---|
| ① | 草稿提及的肢体总数 = 恰好 2 臂 2 手（无"第三/额外/漂浮"字样） | 删冗余描述，回落简单站姿 |
| ② | 若写"手持 X"：明确"一手/双手"，持物件数 ≤ 2 且分属不同手，无"各持多件" | 降级为单手持一物或双手共持一物 |
| ③ | 草稿不含 `third arm / extra hand / extra limb / floating hand / detached` 等词 | 清除并改写 |
| ④ | `ANATOMY` 已含"每手五指"，无需额外；仅校验 ANATOMY 位确实拼入 prompt | 补拼 ANATOMY |

> 自检是"确认环节"的前置关卡，不是出图之后的补救——省下的就是反复重画的额度。

## 5. 确认环节（核心省钱点）

### 5.1 复用现有确认模式

沿用 `v163-CG相册与美术规范.md` §A4.4 的 `confirmModal(title, desc, okText, danger)`(app.js:393，返回 `Promise<boolean>`) 思路，但**确认卡要能展示结构化草稿明细**，故新增一个"出图确认卡"组件（在 `confirmModal` 内嵌结构化列表，或独立卡片，由架构师定）：

- 点击「出图」→ 先 `extractLookBrief(rec)` 提炼 → `validateAnatomy(draft)` 自检 → 自检过才 `renderConfirmCard(draft)` → 用户 OK(`true`) 才调用 `generateImage` / `generateCustom`。
- **未确认绝不调用出图接口**（铁律 2）。
- 与 CG 规范一致："不要进相册时批量弹窗或自动重画，钱是用户的，必须逐张手动确认"。

### 5.2 确认卡结构（展示给用户看的东西）

```
┌─────────────────────────────┐
│ 标题（≤16字，古风）            │
├─────────────────────────────┤
│ 形貌：少女 · 琥珀瞳 · 贝壳簪    │
│ 动作：低眸捧花，身微躬          │
│ 持物：绣球花一束（左手）        │
│ 服饰：黛色襦裙，缠枝纹          │
│ 颜色：发·胭脂(#9d2933)         │
│       衣·黛色(#4a4266)         │
│       里·月白(#d6ecf0)         │
│ 场景：晴窗矮几，午后薄光        │
│ ── 以下两行只读，不可改 ──      │
│ 风格：中式古风（已锁定）        │
│ 一致：与旧像同人同色（已锁定）  │
│ 费用：确认即耗出图额度一，落定难悔│
├─────────────────────────────┤
│      〔就依此画〕  〔容我改改〕  │
└─────────────────────────────┘
```

**字段展示原则**：动作/持物/服饰/颜色/场景 五项是用户能改的；风格/一致性 两行只读；费用行永远在（提醒"钱是用户的"）。

### 5.3 文案模板（中文 · 古风 · 标题≤16字）

**卡片标题候选（选一，均 ≤16 字）：**
- `这般模样，可好？`（7）
- `先瞧一眼再落笔`（7）
- `形象将成，请过目`（7）
- `确认后，方画它`（6）

**按钮文案（短、≤8 字）：**
- 主按钮：`就依此画`（4）／`依此落笔`（4）
- 次按钮：`容我改改`（4）／`我再调调`（4）

**费用提示文案（固定）：**
- `确认即耗出图额度一，画面依上表生成，落定难悔。`

**改写/冲突提示文案（按需出现，古风口吻）：**
- 古风冲突：`「西式衣装」不合古风，已改为中式长衫。`
- 解剖冲突：`双手各持多物易生歧形，已调为单手捧花。`
- 颜色兜底：`此色非常规古色，已取最近传统色「胭脂」。`

### 5.4 回炉流程

用户点「容我改改」→ 回到草稿编辑（改 动作/持物/颜色/场景 任一项）→ 重新 `validateAnatomy` → 重新展示确认卡。**每次改完都要再过自检**，直到 OK 才出图。

## 8. 验收（对这条规范负责）

1. **还原度**：用户人设写"捧着绣球花" → 出图持物必为绣球花，**不是**竹简/卷轴等随机物件。
2. **颜色命中**：用户写"黛色襦裙" → 出图衣物颜色 = 黛色 `#4a4266`（传统色名+色值双写）。
3. **不锁死**：用户没写发型/姿态 → 出图发型姿态各异，不再是固定几套。
4. **解剖拦截**：草稿里出现"双手各持三件/三头六臂" → 自检不过，禁止出图并提示降级。
5. **省钱**：未点「就依此画」前，出图接口零调用；逐张手动确认，无批量预出。
6. **古风不破**：用户写违规西式/日式内容 → 卡片标注已改写，prompt 仍纯古风。
