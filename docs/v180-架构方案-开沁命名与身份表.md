## 四、统一显示解析器（新增，D 批核心）

现状：详情页 `const idCard = spiritIdentityOf(_disp)`（`app.js:6007`），命中才渲染 字/诗/八字。
新增一层包装（**不改动下游渲染行**）：
```js
// app.js
function spiritCardOf(dispName, rec) {
  const idc = spiritIdentityOf(dispName);          // ① 身份表优先（已定 10 位）
  if (idc) return idc;
  const nm = rec && rec.naming;                     // ② 逐串命名（新沁灵）
  if (nm && nm.name) return { name: nm.name, style: nm.style, poem: nm.poem, eight: nm.eight, bead: "" };
  return null;                                      // ③ 回落：不显示字/诗/八字（现有行为）
}
```
详情页只改一处赋值：`const idCard = spiritCardOf(_disp, rec);`
⇒ 其下 `nameShown = (idCard && !rec.nameEdited) ? idCard.name : _disp`（`app.js:6008`）、`idCard.style/poem/eight`（`:6012-6015`）**一个字都不用动** ⇒ **`_test_v175_identity.js:104/106/107` 保持绿**。

## 五、与已定项的关系与顺序（问题 4）

四件事的依赖关系：

```
A 身份表+立绘 ─┐
              ├─> D 开沁命名规格（D 的解析器 spiritCardOf 依赖 A 的"并存"前提；UI 反查也吃 A）
B 主线真名注入 ─┘   （D 写 rec.name 后，B 的注入对新沁灵同样生效 ⇒ 统一口径）
C 关改名 ──────────> 与 D 弱耦合（C 只是移除入口，D 只是新增入口）
```

**建议顺序（同一批做 vs 分批）**：

| 批 | 内容 | 为什么这个顺序 |
|---|---|---|
| **A** | ① 补 `SPIRIT_IDENTITIES` ＋2 条（江冽茗/温茸之）② 补 `MAINCHAR_ART_ALIAS` ＋1 条（`温茸之→粉黛熊`）③ 冰红茶立绘（占位或待美术） | 纯数据、风险低；**先把"10 位显示一致"坐实**，D 才有一致的地基 |
| **B** | `spirits.js` 加 `setCastNameResolver` ＋ `app.js` 注入（对齐 `installGameNameResolver` `app.js:4504-4518`） | 小、独立；让**主线名字条**对 C6/C7 也显真名（A5 的坑） |
| **C** | 关改名入口（运行期隐藏 `#sdRename`，字符串保留） | 极小、独立；随时可做 |
| **D** | 开沁命名规格：字库 + `nameSpecCandidates` + 弹窗 + `rec.naming` 落库 + `spiritCardOf` | 最大块；**依赖 A 的数据与 B 的注入都在位** |

> 结论：**不要四件一次做完**。A、B、C 各自可独立验证（跑测试 + 人工点验），先落这三批把"名字显示"全部统一，再上 D。D 是唯一需要"生成质量"调优的部分，独立成批便于迭代 prompt/字库而不牵动别的。
