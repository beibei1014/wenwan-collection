## 〇、摘要（三句话结论）

1. **改名入口**只有一个：详情页 `#sdRename` 按钮（`js/app.js:6020`）→ `showRenameModal()`（`js/app.js:6573-6605`）→ 写 `rec.name` / `rec.nameEdited`。**关闭零风险**：按当前口径隐藏入口、保留 `nameEdited` 兼容逻辑，老存档（含已改名的 5 只）显示**完全不变**。
2. **性格标签有两层，别混**：用户看到的标签是 `rec.persona.traits`（自由词条，`js/app.js:6022` 渲染）；而「15 种 persona 型别」是 `rec.look.pers`（`js/spirits.js:3694-3699` `personaIdOf`），**只影响送礼偏好 / 恋爱线 / 选角，不直接显示为标签**。现 15 型里 `pampered`（慵懒富贵）够用，但**「城府精明」无对应型**、「外邦憨厚/沉默踏实」只能近似（建议**不新增型别**，改走"型别 + 词条"双写）。
3. **开沁没有命名步骤**：`Spirits.born()`（`js/spirits.js:488-510`）只掷性别、不落名；当前"沁灵名"实为 `rec.name → rec.persona.name（AI 昵称）→ 手串名`（`js/app.js:4459`）。要接命名规格，**钩子应加在 `js/app.js:1309` 调 `born()` 之后**（app 层才够得着身份表），且**新沁灵的四件套从哪来（自动生成 / 手填）尚未定案**，须先拍板。

### A4. 关闭方式（两条，推荐第 1 条）

**方式①（推荐）· 只隐藏入口，不动写入口**
把 `js/app.js:6017-6020` 的三元恒取"已改过名"分支（或加一个集中开关常量），使按钮永不渲染；`showRenameModal` 保留但不可达（或在其开头 `return;` 兜底）。
- 影响面：**1 处渲染**（+ 可选 1 处守卫）。
- 老存档影响：**无**。`rec.name`、`rec.nameEdited` 原样保留；`nameOf`（4461）继续优先 `rec.name`；已改名的 5 只（陆临崖/苏栖盏/沈青舒/谢凝渲/顾时笙）显示不变；未改名的 3 只（柿宝/金算盘/咸法酪）继续走身份反查显示真名。**这是"零回归"的关键。**

**方式②· 禁用写入**
在 `showRenameModal`（6573）或保存回调（6590）开头直接 `return`/`toast("名字由命名规格统一起，暂不可改")`。入口仍可见但点了无效。
- 影响面：**1 处**，但体验差（按钮留着骗点击），不推荐单独用。

**⛔ 禁区（务必遵守）**
- 不得改 `ww_spirits` key：`js/spirits.js:11` `const STORE_KEY = "ww_spirits";`
- 不得碰 `hashStr`：它决定外观（发色/发型/姿态，见 `js/spirits.js:2604`、`2153`）与性别兜底（`rollGender` 484 / `legacyGender` 486）——改它=全库外观漂移。
- 不得改 `rec.nameEdited` 的语义（多处消费点依赖它），除非同步改所有下游。

### A5. ⚠️ 关键副作用（务必先定）
**主线名字条走 `castDispNameOf`（`js/spirits.js:7183-7186`），它只读 `rec.name`／`rec.persona.name`，⛔ 不做身份反查**（与详情页 `spiritIdentityOf` 不同口径）。
- 已在身份表内、且 `rec.name` 已是正式名的那些（见附录），主线显示**正常**。
- ⚠️ **真正的坑在"新沁灵"**：C6 江冽茗（手串名冰红茶）、C7 温茸之（手串名粉黛熊）**尚未进身份表**，若按其手串名落在 `rec.name`（且以后不再允许改名），则详情页可反查到真名、**主线名字条却会印「冰红茶 / 粉黛熊」**。
⇒ **若要"关改名 + 主线显真名"两全**，应给 `castDispNameOf` 加身份反查（对齐 `spiritIdentityOf`），或由命名规格把 `rec.name` 一次性写成真名（见 §方案三）。二者都不碰 `hashStr`，安全。
- 补充：`rec.name` 的**实际值存在用户 localStorage**，代码侧读不到（见 §H），故"哪些还是手串名"只能由用户在浏览器侧核对。

### D1. 代码路径
1. 用户在状态弹层把 `playStatus` 切成 `"done"`（已挂瓷）→ **`js/app.js:1298-1314`**，`st === "done" && prev !== "done"` 时调 **`Spirits.born(item)`**（`js/app.js:1309`）。

4. 另一处 `born()` 调用：补全历史数据时 `js/app.js:8677`（`if (!s[it.id] || !s[it.id].bornAt) Spirits.born(it);`）。

### D2. 命名发生在哪一步？
**没有命名步骤。** `born()` 不写 `rec.name`；开沁那一瞬玩家看到的是 toast「开沁了！是只👦男孩子」（`js/app.js:1311`），名字此时为空串，随后由显示层回落：`rec.name(空) → rec.persona.name(AI/本地昵称，`localPersona` 2606`) → 手串名`（`nameOf`，`js/app.js:4459`）。
⇒ 现状"新沁灵名"其实是**手串名或 AI 随机昵称**，正是用户要改的点。

### D3. 命名规格的接入钩子

### H1. 建议操作方式（请用户配合，一次即可）
让用户在**游戏页**（同源）打开浏览器 Console，粘贴下面任一：

```js
// ① 列出所有沁灵：id / 当前显示名 / 手串名(若有) / 是否改过名 / 性别 / stage
(() => {
  const s = JSON.parse(localStorage.getItem('ww_spirits') || '{}');
  const out = Object.keys(s).map(id => ({
    id,
    name: s[id].name || (s[id].persona && s[id].persona.name) || '',
    nameEdited: !!s[id].nameEdited,
    gender: s[id].gender || '',
    stage: s[id].stage || 1,
    spirit: s[id].spirit !== false,
  }));
  console.table(out);
  console.log('共 ' + out.length + ' 条沁灵记录');
  return out;
})();
```
```js
// ② 直接导出为可粘给我的文本
copy(JSON.stringify(Object.entries(JSON.parse(localStorage.getItem('ww_spirits')||'{}'))
  .map(([id,r]) => ({ id, name: r.name||'', personaName:(r.persona&&r.persona.name)||'' })), null, 0));
```

> ⚠️ 手串名（`item.name`，如"冰红茶/粉黛熊"）**不在 `ww_spirits`**，而在手串库（`bracelets` 表 / 收藏列表）。若要手串名，需导 `bracelets` 或让用户截图收藏列表。
> 💡 也可直接复用 `tools/export.html`：把它改一行为"导出名字清单"，或让用户把 Console ① 的结果发来。

### H2. 由此得出的**待办**
用户需提供一份"我在册的沁灵清单"（id + 手串名 + 是否已改名），才能：
1. 判断还有哪些"未列进核心 10 位"的沁灵需要命名（用户诉求 #2 的"先把清单摆出来"）；
2. 校验 §G1 的 10 位是否与用户实际持有一致；
3. 为"非核心沁灵"批量化命名（按 v180 命名规格）。
