### 1.2 「沁」这个词为什么站得住（美术侧的证据链）

它不是新造词，**本来就是这个 APP 的行话**——`js/tips.js` 里 6 处：

| 出处 | 原文 |
|---|---|
| `tips.js:409` 正式术语条目 | 「**汗沁**：汗液中的成分渗入珠子孔隙，让颜色变深变润的过程。」 |
| `tips.js:370` | 「等表面**沁入**油脂后再上手」 |
| `tips.js:373` | 「让包浆一层层**沁进去**」 |

**美术侧的直接收益**：我在 8 张 CG 里写的质感描写（油脂感、包浆变深、颜色由浅入深、玉化）跟这三条是**同一套语言体系**，不需要额外解释玩家就能懂。
配套还有两条可以直接拿来当禁含判据的依据：
- `tips.js:411` **玉化** ——「盘玩到极致，质地变得像玉石一样通透、坚硬、光亮，是文玩盘玩追求的**终极效果**」
  → 这正是 CG-07 石心的现实原型。所以 CG-07 的「半透明指节」是**玉化的视觉化**，不是凭空玄幻。
- `tips.js:410` **开片** ——「表面因干湿/氧化出现的细小裂纹纹理」
  → 所以 CG-07 的禁含清单里**「禁裂纹」是有依据的**：开片是自然老化，**玉化不是碎裂**。画成裂纹会把"修行圆满"误读成"修行崩坏"，直接毁掉这条反转。

### 1.3 全书结构骨架 → 视觉隐喻（**沁线**）

> **沁 → 开沁（诞生）→ 深沁（突破）→ 沁透（亲密度满档）→ 沁过头 = 石心（终极威胁）**

这条链的意思是：**玩家每点一次「✨ 可深沁」，都是在把石心往前推一步。**
这是全书最狠的一笔，也是**唯一一个"系统 UI 能反向叙事"的位置**。美术侧给出三档呼应（架构师按优先级落）：

| 优先级 | 位置 | 视觉做法 | 成本 |
|---|---|---|---|
| **P1** | **CG-08（终章）** | 中间那道细光 = **沁线**。它必须是**极细、极淡、冷白**（≤2px，`#EAF2F0`）—— 满档「沁透」的沁线看起来反而**最不起眼**。这是点题：**最深的羁绊没有特效。** | 0（已在详卡里） |
| **P2** | **相册：沁线进度条** | 相册计数头 `.album-head` 下方加一条 1px 横线，按 `已收集数 / 8` 从左往右填 `--gold`；**收集到 CG-07（石心）那一格时，那一段换成灰白 `#9FB6AE`（玉色）** —— 进度条自己说出"沁过头了"。 | 低（一条 div + 一个 class） |
| **P3** | **「✨ 可深沁」按钮** | 每深沁一次，按钮金色描边**亮一档**；到石心章阈值时，描边从 `--gold` 变**玉色 + 描边变脆（1px 实线 → 1px 虚线）**。玩家看到按钮"变脆"，却不知道为什么 —— 直到第 11 章揭晓。 | 中（要动现有按钮） |

> P2/P3 都依赖架构师先把 `bond` / `plays` / `stage` 暴露出来（文案策划稿 §5.1 标 🔧 的门槛字段）。
> **P1 不依赖任何新字段，出图即可生效，优先做它。**

### A4.2 分组方式：**按卷分组**（决策 + 理由）

| 候选维度 | 结论 | 理由 |
|---|---|---|
| **按主线卷（卷一~卷五）** | ✅ **采用** | 与主线结构同构；卷名（`卷一 · 醒`…）是**已公开的定稿信息，不剧透**；玩家能感知"卷三还差 2 张"，有收集推进感 |
| 按时间（收集日期） | ❌ | 主线 CG 是**按固定章节顺序**解锁的，时间分组 ≈ 编号分组，且新玩家看不出"还差几张" |
| 按「已收集 / 未解锁」二分 | ❌ | 把所有未解锁堆在底部 = 告诉玩家"你还有 N 张没拿"，且破坏了"这一卷讲完了"的叙事节奏 |

**关键规则：未解锁格子必须在所属卷内原位占位**（不是隐藏、不是堆到末尾）。
这样卷头能显示 `卷三 · 险 1/2`，玩家知道"这卷差一张"，但**看不到那张是什么**。

### A4.3 未解锁格子（防剧透铁律）

| 规则 | 内容 |
|---|---|
| ① | **不显示缩略图、不显示任何剪影/轮廓/局部**——格子内只有 🔒 和门槛文案 |
| ② | **标题一律「？？？」** ——禁止出现 `石心`、`压箱`、`蜕形` 等章节名（第 11 章是全书终极反转，格子里露一个字就废了整条线） |
| ③ | 文案只能来自**门槛字段** `cg.need`（如「读完第 3 章解锁」「到「蜕形」解锁」），**禁止**从章节梗概/台词生成 |
| ④ | 无按压缩放（`transform:none`）、无阴影、无 `cursor:zoom-in` |
| ⑤ | 点击反馈 = 抖动 220ms + toast「还没到时候」；**不跳转、不弹窗、不剧透** |

### A4.4 第五态 `missing` —— 换设备后「图不在本机」

> **背景（team-lead 补充的硬约束，我原版漏了）**：`ww_spirits` 走整库同步跨手机，但 **IndexedDB 是本地的、不同步**。
> 玩家换手机后会看到「已收集 8/8」，但点开全是空的。必须有第五态。

**判定**：元数据在（主 store 里有 `CG-05: { at, title, … }`）**且** IndexedDB 里查不到像素 → `missing`。

**与其他四态的区别（这是本态的关键，别做混）**

| | `locked` | `pending` | `failed` | **`missing`** |
|---|---|---|---|---|
| 解锁了吗 | ❌ 没解锁 | ✅ | ✅ | ✅ **已收集** |
| 曾经画成功过吗 | — | — | ❌ **从没成功过** | ✅ **画成功过** |
| 像素在哪 | — | 生成中 | 无 | **在原来那台设备上** |
| 编号角标 | ❌ 无（标题「???」） | ❌ | ❌ | ✅ **有（05）** |
| 显示真实标题 | ❌ 禁止 | ❌ | ❌ | ✅ **可以**（已收集 = 无剧透风险） |
| 边框 | 虚线 | 虚线 | 虚线 | **实线** |
| 可点 | ❌（只抖动） | ❌ | ✅ 重画 | ✅ 重新生成 |
| 是否花钱 | — | — | ✅ | ✅ |

> **`missing` 的视觉必须同时避开两个误区**：
> - 不能长得像 `locked`（虚线 + 🔒 + 无编号）→ 玩家会以为**进度丢了**，这是最坏的误解；
> - 不能长得像已收集（有缩略图）→ 点开是空的。
> 解法是那三件套：**实线边（区别于 locked 的虚线）+ 保留编号角标（证明"你有了"）+ 斜纹空底 + `☁`**。
> 图标用 **`☁`** 不用 `📱`：☁ = "图在别处"，而 📱 容易被读成"就在这台手机上"，正好和要表达的相反。（以架构师字符串表为准）

**文案（单一样本 = 代码里的字符串表，UI 不许自己硬编码）**

### A4.6 主串分册（多主串 · 主串集 >1 只才出现）

> 补录来源：互动设计师。两轮改动：
> ① 第一轮：**换主串时旧主串的 8 张 CG 不删**，相册要能区分；
> ② 第二轮（用户新需求）：**主串从「1 只」变成「一组」** —— 手动勾选（不限数量）∪ `star>=5` 自动纳入，都空则兜底「开沁最早那只」。所以是 **N 只 × 8 张**。
> 我原版连①都漏了。而且它不是"加个角标"就完事，**它同时改变"已收集 N/8"的分母**，必须做成独立分册。

#### 🔴 第一铁律：收集度**每只各算 N/8**，绝不能跨串求和

分母 `8` 是**按串**的。跨串求总会出现：

> 主串 A 拿 3 张 + 主串 B 拿 5 张 = **`8/8` 已满** ← **假满**

玩家看到 `8/8` 就以为集齐了、不再收集，其实每只都只拿了一半 —— 而**"逐只各走 12 章"正是这套叙事的骨架**。
**这个假满会同时毁掉收集欲和叙事结构**（比换主串后分母变 `11/8` 更隐蔽、更致命）。

| 做法 | 判定 |
|---|---|
| 每只主串**一行/一组**进度：`「小满」已收 3 / 8` | ✅ 采用 |
| 想要全局感 → `共 2 只主串，已收 8 张`（**不给分母**） | ✅ 采用 |
| `已收集 8/8`（跨串求和） | ❌ **禁止** |
| 百分比（`62%`） | ❌ 禁止（沿用原有纪律，只是分母口径改成 per-owner） |

**口径总表**

| 项 | 规则 |
|---|---|
| 「已收 **N/8**」的分母 | 🔴 **每只各算**。分母恒为 `8`（`Spirits.CG_TOTAL`，不硬编码） |
| 全局计数 | 只报 **只数 + 总张数**，`共 N 只主串，已收 M 张`（M = 各只之和，**绝不给分母**） |
| 旧主的 CG | **不删、不失效、可正常看大图** —— 移出主串集 ≠ 作废。**重新勾回来直接复用，不重画、不花钱**（key 匹配即命中缓存） |
| `locked` 在旧主视图 | **不渲染**。旧主已经走完那段路，"未解锁"这个概念在它身上是错的 —— 显示 locked 会暗示"还能再解锁" |
| 分组顺序 | **每只各自按卷分组**，不是把 N 只混在一起按卷排（否则"这一卷讲完了"的节奏会散掉） |
| 常驻吗 | **只有主串集 > 1 只时才渲染筛选条**。默认单主串的玩家永远看不到它，表现和原版一样 |
| 要不要第六态 | **不用**。五态（`ready`/`locked`/`pending`/`failed`/`missing`）完全够用 —— 移出主串集只是"看哪个视图"的问题，不是新的格子状态 |

**数据来源 —— 与互动设计 §C.2「主串集合制」对齐（设计已定稿，判定布尔即 `isMain`）**

> 📌 **已与 `v163-互动系统设计.md` §C.2 对齐**：主串从「单值」改为「**有效主串集**」（`mainSetOf()` 返回 `Set<string>`，元素为串 id）。「这只现在还算不算主串」的布尔**直接复用已有的 `when` 键 `isMain` / `isMainIn`**，**不新造 `isActive`**（§C.2.6 已明确：`albumGroups` 用 `isMain`）。
> - `soloEnv.isMain`（`spirits.js:3425` 一带）= `env.mainSet.has(item.id)`，Set 成员判定；
> - `thEnv.isMainIn`（`:3684` 一带）= `ms.some(m => env.mainSet.has(m.id))`，会话内任一只在集内即 true。
> 原 `storyMainId()`（单值）已由 `mainSetOf()` 取代；相册只消费 `albumGroups()` 返回的 `isMain` 布尔，**不自己算主串集**。

**相册对外的接口要求（与 §C.2.6 `albumGroups` 对齐）**

| # | 要求 | 说明 |
|---|---|---|
| ① | **按 `ownerId` 分组的列表** | 每只一串一项，含 `{ ownerId, name, cgs, got, total, isMain }`。`rec.cgs` 本来就**每串一份**、`CG_TOTAL=8` 也**按 rec 算** → 多主串天然支持，**不需要新存储结构** |
| ② | **每项带布尔 `isMain`：这只现在还算不算主串** | `isMain === mainSet.has(ownerId)`。`true` = 当前主串组，`false` = 旧主组（图不删、计数不掉）。**复用现有 `when` 键，不新造字段** |
| ③ | **`total` 恒定 = 8（per-owner）**，`got` = 该串自己的已收集数 | 🔴 见上方第一铁律，**绝不给跨串分母** |

> **命名纪律（沿用 §C.2，同一概念只留一套词）**：`isMain` / `isMainIn` 是**已存在的 `when` 判定键**（`WHEN_KEYS` 表），剧本作者已在用；相册不再造 `isActive` 第三套词，否则后人必踩。下面 HTML 里的 `data-owner` 与 `.old` class 都不依赖字段名，可直接实现。

### A5.2 手势与操作表

| 操作 | 手势 | 反馈 | 备注 |
|---|---|---|---|
| **切换** | 左右滑动（位移 >40px 或 >0.3px/ms） | 跟手位移 0ms；松手吸附 **220ms `--ease-out`** | 到头时位移减半 + 阻尼回弹 |
| **关闭** | ① 点 ✕ ② 点图片外的黑色区域 ③ **下滑 >80px** ④ ESC ⑤ **安卓返回键** | 淡出 200ms + 图片 `scale(1→.98)` | ⑤ 必须做：`pushState({cgViewer:1})`，`popstate` 时关查看器而非回上一页 |
| **放大** | 双击（`touchend` 间隔 <300ms 且位移 <10px） | 放大到 2×，以双击点为 `transform-origin`，**200ms `--ease-spring`** | 放大后单指拖动平移；再双击复位 |
| **保存** | ① 长按 ≥480ms ② 右下「保存这张」按钮 | 长按 → 弹确认层（160ms）**而非直接保存**，防误触 | 见 §A5.3 三级回落 |
| **单击图片** | 无操作 | — | 刻意留空，避免误关 |

> ⚠️ **「长按保存」是 PWA 的必做项，不是可选项**：iOS Safari 对 data URI 的 `<a download>` 支持不稳，系统级「长按图片 → 存储到照片」是 iOS 上**唯一可靠**的存图路径。所以：
> - 图上**必须**是原生 `<img>`（不能被 `pointer-events:none` 的兄弟层盖住，否则长按菜单出不来）；
> - 长按后弹的确认层要提供「保存到相册 / 取消」，走 §A5.3 的回落链；
> - 长按菜单弹出期间**禁止**触发页面滚动/关闭。

### A5.3 保存的三级回落（CG 是 data URI，必须写全）

```
① navigator.canShare({files}) && navigator.share({files:[new File([blob],'CG-01.jpg',{type:'image/jpeg'})]})
   → iOS 会给出「存储到照片」，最优路径
② 回落：<a download="沁灵纪-CG-01-开沁之夜.jpg" href="{dataUri}"> + a.click()
   → 安卓 Chrome / 桌面可用
③ 再回落：toast("请长按这张图，选「存储到照片」")
```
data URI → Blob：`fetch(dataUri).then(r => r.blob())`（同源 data: 可用）或手动 `atob` + `Uint8Array`。
文件名规范：`沁灵纪-CG-{两位编号}-{标题}.jpg`（例 `沁灵纪-CG-01-开沁之夜.jpg`）。

## A6. 结论：相册大图**不复用** `openSpiritViewer`

**结论：另做 `#cgViewer`。现有 `openSpiritViewer` 一行都不要改，3 个老调用点保持不动。**

| # | 理由 |
|---|---|
| 1 | `openSpiritViewer(src)` 是**单图、无状态**的——每次调用都执行 `$("#viewerNav").innerHTML=""` 并只挂 close。它脑子里没有"图集"，加左右切换 = 重写，不如新写 |
| 2 | 相册要额外 4 块 UI（标题 / 题词 / meta / 计数 / 保存按钮），塞进 `#viewer` 会让「从精灵详情页点立绘」莫名长出相册底栏，或反之 |
| 3 | `.viewer img { flex:1; object-fit:contain }`（`style.css:514`）让图片吃满剩余高度，无法在其下方叠常驻信息栏 |
| 4 | 现有 3 个调用点（`.ft-cgimg` 节令 CG / `#sdCg` 精灵 CG / 房间剧情 CG）走的是"单图看看"的心智，动它会引入回归 |

**但要复用它的 2 个基建，避免两份重复代码：**

| 复用项 | 做法 |
|---|---|
| 关闭手势逻辑 | 抽一个 `bindViewerDismiss(el, closeFn)`：背景点击 / ✕ / ESC / 下滑 / popstate，**`#viewer` 与 `#cgViewer` 共用** |
| 层级与双态切换 | 沿用 `hidden` + `.show` 的显隐方式、`rgba(0,0,0,.92)` 遮罩、38px 圆形关闭按钮（`#cgViewer` 用 z-index 210） |

> 老调用点不变：`openSpiritViewer(src)` 继续服务立绘与单张 CG。
> 只有相册格子点开走 `openCgViewer(list, index)`。

**硬性排版纪律（由对比度反推）：**

1. `--text-2` 在浅色下 **4.26:1 < 4.5:1** → **只能用于 11px 及以上的辅助信息**（meta、箭头、卷头计数），**不能**用于题词、副标题、未解锁提示。
2. `--gold` 浅色下 **3.1:1** → **只能用于 ≥12px 的粗体数字**（`已收集 3/8` 里的 `3`），不能做正文色。
3. 未解锁格子的 `need` 文案用 `--wood-2`（7.8:1），不用 `--text-2`。
4. 圆角：格子 `--r-sm`(10px) < 卡片 `--r-md`(14px)。阴影：格子 `--shadow-1`；入口卡 `--shadow-1`。
5. 深色主题**自动跟随**——因为全部走变量。本文件里出现的裸色值只有 3 处且都是合法例外：遮罩 `rgba(0,0,0,.92)`、`#cgViewer` 信息区的浅色文本（深底场景）、`--font-hand` 楷体。

## A9. 规模与性能约束（8 张起，后续几十张）

| 问题 | 规范 |
|---|---|
| **大图查看卡顿** | `.cg-viewer-track` 内**只保留当前 ±1 共 3 个 `.cg-slide`**，滑动结束重建（虚拟化）。几十张也不会涨 DOM |
| **宫格图片加载** | 宫格**只加载 `thumb`(384)**，大图查看才取 `full`(512)。**禁止**把 512/768 塞进 116px 的格子。两档规格见下表 |
| **首屏渲染量** | 首屏最多渲染 **24 格**；底部放哨兵元素，IntersectionObserver 触底再追加 24 格 |
| **decoding** | 所有 `<img>` 加 `decoding="async"`；`loading="lazy"` 对 data URI 无效，靠上面的分页兜 |
| **滚动** | 宫格容器不自己滚，用页面滚（与现有 `.view` 一致）；sticky 卷头 `z-index:5` |
| **图片解码抖动** | 格子用 `aspect-ratio:4/3` 硬撑高度，**图片加载完不会引起重排** |
| **重画节流** | `.failed` / `.missing` 的按钮点击后立刻置灰 + 文案改「正在画…」，防连点烧额度 |

### 图片规格阶梯（**两档** · 以架构师已落库的代码为准）

> ⚠️ **本节已按实际落库代码修正。** 我初稿写的是三档 384/512/768 并存，架构师实现时选择 **主线 512 + 缩略图 384**（`app.js:2754-2757`），并把 **768 留给旧的 v125 单张突破 CG 路径**。
> 代码是最终事实，规范跟代码走 —— 我原来的 768 会让架构师按 768 生成（8 张 ≈ 1.6MB，白花一半空间）。

| 档 | 长边 | 质量 | 用途 | 存在哪 | 常量（代码事实） |
|---|---|---|---|---|---|
| `thumb` | **384** | JPEG **0.72** | **相册宫格**（格子 116px 视觉宽，384 已 3.3× 超采样） | IndexedDB `ww_cg` · store `pixels` · 同条目字段 | `CG_THUMB_SIZE = 384` / `CG_THUMB_Q = 0.72` |
| `full` | **512** | JPEG **0.72** | **`#cgViewer` 大图查看**、入口卡封面、分享长图 | 同上 | `CG_MAIN_SIZE = 512` / `CG_MAIN_Q = 0.72` |
| ~~768~~ | 768 | 0.86 | **主线 CG 不用**。768 只服务 v125 的单张突破/化形 CG（`CG_IMG_SIZE = 768`，`app.js:2700`），那条路**一行不动** | 主 store `rec.cgUrl`（旧机制） | `CG_IMG_SIZE = 768` |

### ✅ A10.1 共享 store 的 key 必须带 owner（多主串引入的真 bug · 已解决 9537ef2）

> 这条是互动设计师查出来的，**已确认是真 bug 不是理论风险**，已于 `9537ef2` 修复（像素 key 改为 `ownerId|id`）。存档留痕。

**历史问题（已于 `9537ef2` 修复）**：`ww_cg` 是**共享 store** —— N 只主串的像素全在同一个库里。旧实现里，
key 生成是 `cgPutPixels(id, pixels)` → `String(id)`，`id` 就是 `"CG-01"`，没有任何 owner 信息：

```js
// spirits.js:183（修复前 · 危险）
function cgPutPixels(id, pixels) {
  const key = String(id);        // ← "CG-01"，多主串同名 CG 互相覆盖
```

**修复后（`9537ef2`）**：签名加 `ownerId` 前缀，像素 key 改为 `ownerId|id`：

```js
// spirits.js:183（已修复 · 9537ef2）
function cgPutPixels(ownerId, id, pixels) {
  const key = String(ownerId) + "|" + String(id);   // ← "sp_7710|CG-01"，按 owner 隔离
```

**修复前的后果**：主串 A 的 `CG-01` 和主串 B 的 `CG-01` → **同一个 key** → **互相覆盖**。
玩家切一次主串，两个都变成最后画的那一张。**放大的话**：所有没设 `appearanceSeed` 的串（默认 `0`）全糊成一张图。

**修法（已于 `9537ef2` 修复并落库）**：像素 key 改为 **`ownerId + "|" + id`**（如 `sp_7710|CG-01`）。`ownerId` 取串 id，把各主串的同名 CG 像素彻底隔离；`id` 仍是 `"CG-01"` 这类 CG 编号。

> 为什么不用 `variant/appearanceSeed/gender/provider` 拼进 key：这些只在「同一只换形象」时变，而换形象本就会作废对应 CG（见 §A10.2 失效矩阵），不构成覆盖风险；真正会撞 key 的只有「不同 owner 的同名 CG」，一个 `ownerId` 前缀就解决。
> 元数据 `rec.cgs[id]` 仍 **per-owner** 存放（每只串一份 `rec`），与像素 key 的 `ownerId` 同源：一条 CG 记录 = `(ownerId, id)`，换主串是新增记录而非改写（见 §B0 元数据表 / 互动设计 §C.2.6）。

**对相册的影响**：**零**。宫格、五态、两档尺寸、分册全不受影响 —— 因为相册只消费 `cgSlotOf()` 的返回，不自己拼 key。
**但**：如果相册为了做 `#cgViewer` 的虚拟化预取而自己拼过 key，**必须跟着改**。我核对过本文档 —— **没有拼过 key，全部走 `cgSlotOf()`**，安全。

#### ⚠️ 改 key 时顺带要处理：旧 key 下的像素会变孤儿

key 从 `"CG-01"`（旧：`String(id)`）改成 `ownerId|id`（如 `sp_7710|CG-01`）之后，**已经用旧 key 存进去的像素按新 key 查不到** → 已出过图的玩家一升级，所有 CG 格子在相册里都会变 `missing`（元数据在、像素"不在本机"）。

| 口径 | 评价 |
|---|---|
| **加一次性迁移**（循环读旧 key `CG-01`…`CG-08`，写到新 key） | ✅ **推荐**。逻辑就是读-写两行，成本极低，老用户 CG 不丢 |
| 不管，让用户自己点「重新生成」 | ❌ 老用户白花额度（N 只 × 8 张），且触发时还得逐个弹 `confirmModal` —— 体验是"升级一次，收藏全没了" |

> 这条不在相册 UI 范围内（属存储层），但**它直接决定相册格子升级后是亮着还是变 `missing`**，所以写在规范里留档。
> 判断依据很简单：**`missing` 是给"换设备"这种真·不可抗力准备的，不该被一次代码升级批量制造出来。**

### 🔴 A10.2 「已收集」判定必须以元数据为准

> ### 🔴 **「已收集」判定必须以元数据为准，不能以"图还在不在"为准。**
>
> 违反这条会出现三种具体事故：
> ① 出图失败 → 格子被判成"未解锁"，**把已解锁内容倒退回剧透状态**；
> ② 配额被裁 → 玩家看到"昨天还在的 CG 今天没了"，且计数从 8/8 掉回 7/8；
> ③ 换设备 → IndexedDB 没同步，8/8 全变空。
> 正确做法是：**元数据定生死，像素只定显示形态** —— 元数据在而像素不在，就是 §A4.4 的 `.missing`，不是 `locked`。

**换设备是必须处理的（team-lead 补充的硬约束）**：`ww_spirits` 走整库同步跨手机，但 **IndexedDB 是本地的、不同步**。
所以 UI 侧准备了第五态 `.album-cell.missing`（§A4.4），架构师侧需要保证：

| 架构师要做 | 说明 | 状态 |
|---|---|---|
| 元数据随主 store 同步 | `rec.cgs[id]` 走 `ww_spirits`，**跨设备一定在** | ✅ 已实现 |
| 像素只存本地 IndexedDB | 查不到 → `cgStateOf` 返回 `missing`（不报错、不自动重画） | ✅ 已实现 |
| **`ww_cg` 的 key 加 owner（`ownerId\|id`）** | 见 §A10.1 —— 多主串同名 CG 不再互相覆盖 | ✅ **已解决（9537ef2）** |
| **禁止进相册时批量重画** | N 只 × 8 张 × 1 次额度，钱是用户的。必须逐张手动确认（§A4.4） | 规范已定 |
| 首次检测到 ≥1 张 `missing` | 计数头下方出一条一次性提示条：`有 3 张的图在原来那台设备上`，点它滚到第一张 `missing`。**不要弹窗轰炸** | 规范已定 |

## A11. 状态机与文案总表（**state 名与 class 名以代码为准**）

> 代码里的 state 名（`spirits.js:254-286`）与本文件的对应关系：
> `ready` = 已收集且像素在本机 · `collected` = 已收集但还没查像素 · `locked` / `pending` / `failed` / `missing` / `placeholder` 同名。
> UI 一律用 `cgCellClass(state)` / `cgCellHint(state)` 取值，**不许自己硬编码字符串**。

| state | class | 视觉 | 文案 | 可点 |
|---|---|---|---|---|
| `ready` / `collected` | `.album-cell` | 缩略图 + 编号角标 | — | ✅ 开大图 |
| `locked` | `.album-cell locked` | 灰**虚线**底 + 🔒 · **无编号** | `cg.need \|\| cgCellHint('locked')`（见 §A4.4 冲突说明） | ⚠️ 只抖动 + toast |
| `pending` | `.album-cell pending` | 灰虚线底 + 转圈 · 无编号 | 「正在画…」 | ❌ |
| `failed`<br>（从没成功过） | `.album-cell failed` | 灰虚线底 + ↻ · 无编号 | 「画失败了 · 点一下**重画**」 | ✅ 重画 |
| `missing`<br>（画成功过·换设备） | `.album-cell missing` | **斜纹空底 + 实线边 + 有编号** + **☁** | 「这张在原来那台设备上」<br>「点一下**重新生成**」 | ✅ 确认弹窗后重新生成 |
| `placeholder` | `.album-cell placeholder` | 米色底 + 虚线 + 文字 | `CG-01 · 待画` | ❌ |

> **四态区分口诀**：`locked`=没解锁 · `failed`=没画成 · `missing`=画成了但图不在这 · `pending`=正在画。
> **`failed` 说「重画」，`missing` 说「重新生成」** —— 措辞不同是因为后果不同：前者是第一次，后者可能和原来那张不一样。
> **多主串不引入第六态**（§A4.6）：切主串只换视图，格子状态不变。

## B6. ⚠️ 交付纪律：任意 js/css 改动都必须 bump 对应 `?v=`

> 补录来源：我核 `014ce61` 发现该提交**唯一 UI 改动**就是版本号（`index.html` 30 行 `?v=20261118` → `?v=20261128`，`sw.js` 从 `wenwan-v163` → `wenwan-v164`）；近期修 `cgPutPixels` 撞 key 的 `9537ef2` 又 bump 了 `spirits.js` / `app.js` 到 `20261129`。

**规则（覆盖任意 js/css 改动，不只 CSS）**

|---|---|---|---|
| ① | 改了**任意一个**带 `?v=` 的 js / css（含 `spirits.js` / `app.js` / `skin.css` …） | 把**那个文件**的 `?v=` 戳换新 | 各文件戳独立：`spirits.js?v=20261129`、`app.js?v=20261129`、`skin.css?v=20261128` 互不牵连 |

| ③ | `sw.js` | **无需动** | `sw.js` 走**网络优先 + 缓存兜底**，按 `CACHE` 常量分代；纯 js/css 修复不依赖它重新部署 |

**每次提交自核清单（改动清单）**

- 凡动了 `index.html` 里带 `?v=` 的任一 js/css → 把**那一行**的戳 +1（如 `20261129`）；多文件改动可共用同一新戳。
- `sw.js` **只有缓存策略本身变化**时才动 `CACHE` 常量；普通 js/css bug 修复（如 `9537ef2`）不动它。
- 一次提交同时落地相册和其他任务：**各自 bump 自己改动到的文件**即可，不必每功能各 bump 一遍、也不必凑同一次提交。
